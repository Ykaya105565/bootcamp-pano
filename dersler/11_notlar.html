11 · Day07-RAG Query & AI Agentlara Giriş

Bu derste ne var: Gerçek kullanıcı sorguları "kirli" olduğunda (eksik, genel, gürültülü, çok konulu) klasik RAG'in neden yanlış bağlam getirdiği gösterildi ve dört sorgu iyileştirme tekniği (Rewrite-Retrieve-Read, Multi-Query Retrieval, RAG Fusion, HyDE) LangChain + PGVector üzerinde kodlandı. Dersin son bölümünde AI agent kavramına giriş yapıldı: LLM → araç destekli LLM → AI asistan → AI agent seviyeleri ve agent'ların production'da kullanımı tartışıldı.

Ana kavramlar

  • Klasik (naive) RAG: Soru → embedding → vektör DB'den en yakın k chunk → context + soru → LLM → cevap. Neden önemli: Tüm teknikler bu temelin üstüne bir "sorgu ön işleme" ya da "sonuç sonrası işleme" katmanı ekliyor.
  • Garbage in, garbage out: Bağlam (context) ne kadar temizse cevap o kadar iyi. Kötü sorgu → yanlış chunk → yanlış/sapkın cevap. Neden önemli: Production'da kullanıcı sorguları hiçbir zaman demodaki gibi temiz değildir.
  • Kirli sorgu türleri: eksik soru, çok genel soru, yazım hatası, tek soruda birden fazla konu, gereksiz detay ("ocakta yemek unuttum" örneği).
  • Rewrite-Retrieve-Read (sorguyu yeniden yazma): LLM'e "vektör araması için daha iyi bir sorgu üret, alakasız detayları at" dedirtip yeni sorguyla arama yapmak. Cevap üretilirken orijinal soru prompt'a konuyor. Neden önemli: Gürültülü sorgularda alakasız chunk'ların gelmesini ve modelin gereksiz detaylara tepki vermesini engeller.
  • Multi-Query Retrieval (çoklu sorgu): Aynı sorunun N farklı versiyonunu ürettirip her biriyle arama yapmak, sonuçları birleştirip tekrarları atmak (unique union). Neden önemli: Her soru embedding uzayında farklı bir noktaya düşer; mesafe tabanlı benzerlik aramasının "tek noktaya bakma" sınırını aşar, bağlamı zenginleştirir.
  • RAG Fusion: Çoklu sorgu + sonuçların Reciprocal Rank Fusion (RRF) ile puanlanıp sıralanması. Birden çok listede (ve üst sıralarda) çıkan doküman en üste gelir. Neden önemli: Model bağlamda üstte olana daha çok dikkat eder; en alakalı chunk'ı en başa koymak cevap kalitesini artırır.
  • HyDE (Hypothetical Document Embeddings): Soruya önce LLM'e kısa, varsayımsal bir cevap/pasaj yazdırıp o pasajın embedding'i ile arama yapmak. Neden önemli: Kısa, belirsiz ya da dokümanla farklı dilde/ifadeyle sorulan sorularda soru ile cevap arasındaki "anlamsal mesafeyi" kapatır.
  • @chain dekoratörü: Normal bir Python fonksiyonunu LangChain Runnable'a çevirir (.invoke(), pipe'a bağlanabilir).
  • LCEL pipe (|): Bir adımın çıktısını sonrakine girdi verir: prompt | llm | parser.
  • retriever.batch: Retriever'ı bir sorgu listesi üzerinde toplu çalıştırır → liste-listesi (her sorgu için doküman listesi) döner.
  • Metadata / kaynak (source): Document nesnesindeki metadata sayesinde her chunk'ın kaynağı gösterilebilir. Kullanıcıya cevapla birlikte kaynak göstermek beklenen bir özellik.
  • AI agent: Kendi kendine hareket eden otonom sistem: görevi alır, düşünür, plan yapar, araç kullanır, sonucu değerlendirir, gerekirse planı değiştirir.
  • Araç (tool): LLM'i dış dünyaya açan "el" (API, web araması, kod çalıştırma, DB sorgusu…).
  • AI asistan vs. AI agent: Asistan önemli kararlarda kullanıcıdan onay ister (kontrol kullanıcıda); agent kendi karar verip ilerler.

Akış / mimari

Klasik RAG

Soru → embed → Vektör DB (k en yakın) → [chunk'lar + soru] → Prompt → LLM → Cevap

Rewrite-Retrieve-Read

Soru → LLM (rewrite) → temiz sorgu → retriever → chunk'lar
                                   ↓
          [chunk'lar + ORİJİNAL soru] → Prompt → LLM → Cevap

Multi-Query Retrieval

Soru → LLM → {S1, S2, S3, S4, S5} → retriever.batch → [[d..],[d..],...] → get_unique_union → context → LLM → Cevap

RAG Fusion

Soru → LLM → {S1..S4} → retriever.batch → [[d..],...] → reciprocal_rank_fusion (puanla + sırala) → context → LLM → Cevap

HyDE

Soru → LLM ("passage yaz") → varsayımsal pasaj → retriever (pasajın embedding'i ile) → chunk'lar → [chunk'lar + soru] → LLM → Cevap

AI agent seviyeleri

1. Doğrudan LLM        → zeki ama pasif beyin; bilgisi donuk (bugünkü hava durumunu bilemez)
2. Araç destekli LLM   → Soru → Model ⇄ API/araç → Cevap
3. AI Asistan          → araç kullanır + önemli kararlarda onay ister (Copilot Chat, doküman/araştırma asistanları)
4. AI Agent            → görevi alt görevlere böler → alt agent'lar (backend, frontend, QA tester, technical writer)
                         → geri bildirim → planı güncelle → nihai cevap

Çizimden (derste anlatılmadı / kayıtta yok) — agent nasıl düşünür?

Algıla → Planla → Harekete geç (tools) → Öğren & Değerlendir → (yetersizse tekrar)
  • Algıla: Kullanıcı isteği + bağlam (sistem talimatları, önceki konuşmalar, dosyalar, araçlardan gelen bilgiler = context). Ör. "AI Engineering için 30 günlük çalışma planı hazırla" → hedef ne, konu ne, süre ne, seviye biliniyor mu?
  • Planla: Hedefi alt görevlere böler (seviyeyi belirle, konuları listele, haftalara böl, tablo sun). Kullanıcı bu adımları yazmadı; agent kendisi üretti. Planlama, agent'ı chatbot'tan ayıran en önemli özelliklerden biri.
  • Harekete geç: Araç kullanır (web araması, dosya okuma, DB sorgulama, Python çalıştırma). Seyahat agent'ı örneği: search_flights, search_hotels, weather_search.
  • Öğren ve değerlendir: Araç doğru sonuç verdi mi, görev tamamlandı mı, sonraki adıma geçilebilir mi, plan değişmeli mi, başka araç mı gerekli, kullanıcıdan ek bilgi mi istenmeli?
  • Örnek: "1000 doların altında AI geliştirmeye uygun dizüstü bul" → Algıla (ürün, bütçe, amaç, RAM/GPU/işlemci/depolama) → Plan (ara, özellikleri çıkar, fiyatları kontrol et, en iyileri sun) → Tools (web arama) → Değerlendir (bütçe, GPU yeterli mi, RAM yükseltilebilir mi, fiyat güncel mi) → yetersizse tekrar ara.
  • ReAct (Reasoning + Acting): Düşün → Eylem (Tools) → Gözlemle → (tekrar et) → Cevap.
  • LangChain vs LangGraph: LangChain ile basit, ileri doğru düz akan agent'lar (Kullanıcı → LLM → Cevap); karmaşık agent'lar için LangGraph: START → Agent (karar verir) ⇄ Tools (araç gerekliyse; sonuç döner) → iş bittiyse END. Düğümler (node) ortak bir State'i okur/yazar; kritik karar öncesi durabilir, durumu kaydeder, insan onayı isteyebilir. Her adım checkpoint olarak kaydedilir → 10 adımlık görevde 7. adımda çökme olursa normal program baştan başlar, LangGraph kaldığı yerden devam eder.

Kod / uygulama

Kaynak: 3_rag_queries.ipynb. Veri: docs/antik-yunan-gunluk-yasam.txt (docs.zip içinde). Vektör DB: Docker'da çalışan PostgreSQL + pgvector.

1) Indeksleme (geçen dersin tekrarı)

text = file_path.read_text(encoding="utf-8")
raw_documents = [Document(page_content=text, metadata={"source": str(file_path)})]

text_splitter = RecursiveCharacterTextSplitter(chunk_size=600, chunk_overlap=80)
documents = text_splitter.split_documents(raw_documents)

embeddings_model = OpenAIEmbeddings(model="text-embedding-3-small")

db = PGVector.from_documents(
    documents=documents,
    embedding=embeddings_model,
    connection="postgresql+psycopg://ai:ai@localhost:6024/ai_db",
    collection_name="rag-antik-yunan-2-cohort-demo-01",
    use_jsonb=True,
    pre_delete_collection=False
)
retriever = db.as_retriever(search_kwargs={"k": 2})
  • Document(..., metadata={"source": ...}) → her chunk kaynağını taşır; cevapta kaynak göstermek için.
  • chunk_size=600, chunk_overlap=80 → küçük metin için hocanın önerdiği değerler; overlap chunk'lar arası bağlantıyı korur.
  • text-embedding-3-small → ucuz/küçük embedding modeli (~1536 boyut).
  • connection → Docker'daki Postgres; port 6024. Docker kapalıysa bu hücre asılı kalır.
  • collection_name → aynı koleksiyona ikinci kez yüklersen aynı chunk'lar çoğalır; hoca bu yüzden adı değiştirdi.
  • pre_delete_collection=False → var olan koleksiyonu silmez (True olsaydı önce silip yeniden yazardı). Not: hocanın açıklaması değil, parametrenin anlamı.
  • k=2 → en yakın 2 chunk.

2) Temel QA zinciri

SYSTEM_PROMPT = ("""Answer the question based only on the following context:\n{context}""")
prompt = ChatPromptTemplate([("system", SYSTEM_PROMPT), ("human", "{question}"),])
llm = ChatOpenAI(model_name="gpt-5.6-luna",)

@chain
def qa(input):
    docs = retriever.invoke(input)
    formatted = prompt.invoke({"context": docs, "question": input})
    answer = llm.invoke(formatted)
    return answer
  • based only on the following context → modeli bağlama bağlar (halüsinasyonu azaltır). Geliştirme: "bilmiyorsan bilmiyorum de", rol tanımı.
  • @chain → fonksiyonu Runnable yapar, qa.invoke(query) ile çağrılır.
  • result.content → AIMessage'ın metin kısmı.

3) Rewrite-Retrieve-Read

rewrite_prompt = ChatPromptTemplate.from_template("""
    Provide a better search query for vector search to answer the given question.
    Remove irrelevant details.
    Return only the improved search query.

    Question: {x}

    Improved search query:""")

def parse_rewriter_output(message):
    return message.content.strip('"').strip("**").strip()

rewriter = rewrite_prompt | llm | parse_rewriter_output

@chain
def qa_rrr(input):
    new_query = rewriter.invoke(input)
    print("Rewritten query:", new_query)
    docs = retriever.invoke(new_query)
    formatted = prompt.invoke({"context": docs, "question": input})
    answer = llm.invoke(formatted)
    return answer
  • {x} → şablonda tek değişken olduğu için rewriter.invoke(query) düz string ile çağrılabiliyor.
  • Return only the improved search query → modelin açıklama eklemesini engeller.
  • parse_rewriter_output → tırnak, ** ve boşlukları atar; gereksiz token göndermemek için.
  • retriever.invoke(new_query) → arama yeni sorguyla,
  • "question": input → cevap orijinal soruyla üretilir (kullanıcının asıl niyeti korunur).

4) Multi-Query Retrieval

retriever = db.as_retriever(search_kwargs={"k": 5})

perspectives_prompt = ChatPromptTemplate.from_template("""
    ... generate five different versions of the given user question ...
    Provide these alternative questions separated by newlines.
    Original question: {question}
""")

def parse_queries_output(message):
    return message.content.split("\n")

query_gen = perspectives_prompt | llm | parse_queries_output

def get_unique_union(document_lists):
    deduped_docs = {
        doc.page_content: doc
        for sublist in document_lists
        for doc in sublist
    }
    return list(deduped_docs.values())

retrieval_chain = query_gen | retriever.batch | get_unique_union

@chain
def multi_query_qa(input):
    docs = retrieval_chain.invoke(input)
    formatted = prompt.invoke({"context": docs, "question": input})
    answer = llm.invoke(formatted)
    return answer
  • k=5 → her alt sorgu için 5 chunk (varsayılan 4).
  • separated by newlines + split("\n") → sorguları listeye çevirmek için anlaşma.
  • get_unique_union → dict comprehension iki işi birden yapar: iç içe listeyi düzleştirir ve page_content anahtarı sayesinde tekrarları atar (aynı metin → aynı anahtar).
  • retriever.batch → sorgu listesindeki her sorgu için retriever'ı çalıştırır, liste-listesi döner.
  • Derste: 45 chunk → tekrarlar atılınca 13 benzersiz chunk.

5) RAG Fusion — Reciprocal Rank Fusion

def reciprocal_rank_fusion(results, k=60):
    scores = {}
    documents = {}
    for doc_list in results:
        for rank, doc in enumerate(doc_list):
            content = doc.page_content
            if content not in documents:
                documents[content] = doc
            point = 1 / (k + rank + 1)
            scores[content] = scores.get(content, 0) + point
    sorted_contents = sorted(scores, key=scores.get, reverse=True)
    ranked_docs = []
    for content in sorted_contents:
        ranked_docs.append(documents[content])
    return ranked_docs

retrieval_chain = query_gen | retriever.batch | reciprocal_rank_fusion
  • results → her sorgunun sıralı doküman listesi.
  • enumerate(doc_list) → rank 0'dan başlar (0 = en yakın).
  • point = 1 / (k + rank + 1) → üst sıradaki doküman daha çok puan alır; aynı doküman birden çok listede çıkarsa puanları toplanır.
  • k=60 → yumuşatma sabiti; tek bir listedeki 1. sıranın aşırı baskın olmasını engeller. Not: 60, RRF'de literatürde yaygın kullanılan değerdir; derste ayrıca açıklanmadı.
  • sorted(..., reverse=True) → toplam puana göre büyükten küçüğe; en alakalı en üstte.
  • Multi-Query'den farkı: Multi-Query sadece tekrarları atar (sırasız birleşim), RAG Fusion puanlar ve sıralar.

6) HyDE

prompt_hyde = ChatPromptTemplate.from_template("""
    Please write a passage to answer the question.
    Question: {question}
    Passage:
""")

llm = ChatOpenAI(temperature=0)
generate_doc = prompt_hyde | llm | StrOutputParser()
retrieval_chain = generate_doc | retriever
  • Please write a passage → modelden soru değil, cevap gibi görünen bir pasaj istenir.
  • temperature=0 → varsayımsal pasaj tutarlı/deterministik olsun.
  • StrOutputParser() → AIMessage'ı düz string'e çevirir; retriever string bekler.
  • generate_doc | retriever → arama sorunun değil pasajın embedding'iyle yapılır. Cevap üretilirken yine orijinal soru kullanılır.

Hocanın vurguları & pratik kurallar

  • Bağlam her şeydir: "Konteksimiz ne kadar iyi olursa cevap o kadar iyi olur."
  • Gereksiz chunk/token = hem maliyet hem modelin kafasının karışması. Sadece ilgili kısımları ver.
  • Küçük metinlerde chunk_size ≈ 600, overlap ≈ 80 iyi bir başlangıç.
  • Aynı koleksiyona aynı veriyi iki kez yükleme → tekrar eden chunk'lar gelir; yeni deneme için koleksiyon adını değiştir.
  • Cevapla birlikte kaynakları göster.
  • Model çıktısındaki ", ** gibi süsleri bir sonraki adıma göndermeden temizle (token tasarrufu).
  • Prompt'larla modeli yönlendirmek "çok kolay": ne istediğini ve sadece ne döndürmesi gerektiğini açıkça yaz.
  • Tekniklerin hepsini birden kullanmak çok token harcar; hangisinin işe yaradığını değerlendirme (evaluation) ile ölç (son hafta).
  • HyDE özellikle kısa, belirsiz veya dokümandan farklı ifade edilmiş sorularda.
  • for döngüsü gibi kodları ezberlemene gerek yok; yapay zekâ yazıyor. Ne yaptığını anlaman yeterli.
  • Proje yap, GitHub'a koy, paylaş; günde 2–3 saat pratik.
  • Konular zincir gibi: RAG → Agentic RAG → agent'lar → MCP → ileri agent projeleri.
  • Agent'lar: tek agent'a güvenme; birden fazla agent birbirini kontrol etsin (ileride Reflection mimarisi). Agent bir görevi yapar, işi yöneten/kontrol eden insan gerekir.
  • Alan bilgisi + agent geliştirme becerisi = en güçlü profil. "Angarya işi yapay zekâ yapar, siz karar veren olursunuz."
  • Agent geliştirmede ileride ağırlıklı olarak LangGraph kullanılacak.
  • Sektör görüşü (öğrenciden, hoca onayladı): Rutin, kuralla çözülebilen işleri kodla yap; yapay zekâyı gerçekten gereken yerde kullan (maliyet + güvenlik). Agent'a verilecek yetki ciddi bir tasarım kararı.

Kendini test et

  1. Production'da klasik RAG'in yanlış cevap üretmesine yol açan dört "kirli sorgu" türü nedir?
Cevap

Eksik soru, çok genel soru, yazım hatası içeren soru ve tek soruda birden fazla konu (ayrıca gereksiz detay/gürültü). Bunlar retriever'ın yanlış chunk getirmesine, dolayısıyla LLM'in yanlış cevap üretmesine yol açar.

  1. Rewrite-Retrieve-Read'de arama hangi sorguyla, cevap hangi soruyla üretilir? Neden?
Cevap

Arama LLM'in yeniden yazdığı temiz sorguyla yapılır (retriever.invoke(new_query)); cevap ise orijinal soruyla üretilir ("question": input). Böylece arama gürültüden arınır ama kullanıcının asıl niyeti kaybolmaz.

  1. Multi-Query Retrieval neden işe yarar? "Embedding uzayı" ile açıkla.
Cevap

Her sorgu versiyonu embedding uzayında farklı bir noktaya düşer; her biri kendi yakınındaki chunk'ları getirir. Tek sorgunun kaçırabileceği ilgili chunk'lar da yakalanır, bağlam zenginleşir (mesafe tabanlı benzerlik aramasının sınırını aşar).

  1. get_unique_union fonksiyonu tekrar eden dokümanları nasıl temizler?
Cevap

Dict comprehension ile iç içe listeyi düzleştirir ve her dokümanı page_content anahtarıyla sözlüğe koyar. Aynı metinli doküman aynı anahtarı ezer, böylece her içerikten tek kopya kalır; list(deduped_docs.values()) ile listeye çevrilir.

  1. Multi-Query ile RAG Fusion arasındaki temel fark nedir?
Cevap

Multi-Query sonuçları birleştirip sadece tekrarları atar (sıralama yok). RAG Fusion ise Reciprocal Rank Fusion ile her dokümanı listelerdeki sırasına göre puanlar, puanları toplar ve sıralar; en çok/üst sırada tekrar eden doküman en üste gelir ve model ona öncelik verir.

  1. RRF'de bir doküman iki listede 1. sırada (rank=0) çıkıyor, k=60. Toplam puanı nedir? Tek listede 1. sırada çıkan dokümanla karşılaştır.
Cevap

Her liste için 1/(60+0+1) = 1/61 ≈ 0,0164; toplam ≈ 0,0328. Tek listede 1. sıradaki doküman ≈ 0,0164 alır. Birden fazla listede çıkmak puanı belirgin biçimde artırır.

  1. HyDE'de retriever neyin embedding'iyle arama yapar ve hangi durumlarda tercih edilir?
Cevap

LLM'in soruya yazdığı kısa varsayımsal pasajın (cevabın) embedding'iyle. Soru çok kısa, belirsiz ya da dokümandan farklı bir ifadeyle sorulmuşsa tercih edilir; pasaj daha fazla anahtar kelime içerdiği için daha zengin bağlam getirir.

  1. HyDE kodunda StrOutputParser() neden kullanılıyor?
Cevap

LLM bir AIMessage döndürür; StrOutputParser bunu düz metne (string) çevirir. Zincirin sonraki adımı olan retriever bir string sorgu beklediği için gerekli.

  1. @chain dekoratörü ne işe yarar?
Cevap

Sıradan bir Python fonksiyonuna LangChain Runnable (zincir) özelliği kazandırır: .invoke() ile çağrılabilir ve diğer Runnable'larla pipe'lanabilir hale gelir.

  1. AI agent'ın 4 seviyesini sırala; AI asistan ile AI agent arasındaki fark nedir?
Cevap

1) Doğrudan LLM (zeki ama pasif, bilgisi donuk), 2) Araç destekli LLM (API/araçlarla dış dünyaya açılır), 3) AI asistan (araç kullanır, önemli kararlarda kullanıcıdan onay ister; ör. GitHub Copilot Chat), 4) AI agent (görevi alt görevlere böler, alt agent'lar/araçlar kullanır, geri bildirime göre planı değiştirir, kendisi karar verip nihai cevabı üretir). Fark: asistanda kontrol kullanıcıda, agent otonom ilerler.
