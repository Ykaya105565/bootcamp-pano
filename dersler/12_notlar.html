12 · Day08 – AI Agent Mimarileri

Bu derste ne var: Chatbot ile ajan (agent) arasındaki fark ve yapay zekâ sistemlerinin dört seviyesi anlatıldı. LangChain'in create_agent fonksiyonuyla ilk ajan kuruldu ve ajana Tavily web arama aracı (tool) bağlandı. Ardından LangGraph ile state, düğüm (node), kenar (edge) ve bellek (checkpointer, thread_id) kavramları uygulandı. Son olarak iki temel ajan mimarisi kodlandı: chain (SQL üret → açıkla) ve router (sağlık kayıtları / sigorta belgeleri arasında yönlendirmeli RAG).

Ana kavramlar

  • Chatbot: Girdi → çıktı. Düşünmez, araç kullanmaz. Önemi: LLM'in güncel ve özel veriyi bilememesi sınırını gösterir.
  • Ajan (agent): Görev alır → düşünür → plan yapar → gerekirse araç kullanır → görevi tamamlar. Önemi: LLM'e aksiyon alma yeteneği kazandırır.
  • AI sistem seviyeleri: 1. Sadece LLM (pasif beyin; kavanozdaki beyin), 2. Araç destekli LLM (beyne "el" verilir), 3. AI Asistan (araç kullanır ama önemli kararlarda insandan onay ister; ör. GitHub Copilot), 4. AI Agent (görevi alt görevlere bölüp alt ajanlara dağıtır, geri bildirimle döngüsel kontrol eder).
  • Araç (tool): Ajanın dış dünyaya eriştiği fonksiyon (web arama, hava durumu, spor skoru…). @tool dekoratörü ile tanımlanır. Önemi: Ajan aracı, fonksiyon adı + docstring'e bakarak seçer.
  • Tavily: Ajanlar için web arama API'si. Ücretsiz kotası (aylık ≈1000 kredi) ders için yeterli.
  • LangChain vs LangGraph: LangChain = basit, tek yönlü akış (Kullanıcı → LLM → Cevap). LangGraph = graf tabanlı, döngü kurulabilen, durumu kaydeden, kompleks ajanlar için.
  • Node (düğüm): Grafın bir adımı; sıradan bir Python fonksiyonu. state alır, güncellenecek alanları dict olarak döndürür.
  • Edge (kenar): Düğümler arası bağlantı; veri kenarlardan akar.
  • Conditional edge (koşullu kenar): Bir fonksiyonun döndürdüğü değere göre hangi düğüme gidileceğini seçer (router'ın kalbi).
  • START / END: LangGraph'ta hazır gelen başlangıç ve bitiş düğümleri; ayrıca tanımlanmaz.
  • State: Ajanın hafızası; graf boyunca akan verinin alanları. TypedDict / MessagesState / Pydantic ile tiplenir. Önemi: Tiplemek ajanın yanlış veri tipi üretip uygulamayı "patlatmasını" önler, token tasarrufu sağlar.
  • add_messages + Annotated: Mesajların listeye üzerine yazılmadan eklenmesini sağlayan reducer. MessagesState bunu hazır içerir.
  • Checkpointer (InMemorySaver): State'i her adımda kaydeder → konuşma hafızası. Üretimde PostgreSQL/MySQL gibi kalıcı veritabanları kullanılabilir.
  • thread_id: Her oturum (konuşma) için ayrı bellek. Aynı thread hatırlar, farklı thread hatırlamaz.
  • Kaldığı yerden devam: LangGraph sonuçları sakladığı için 7. adımda hata çıkınca, düzeltildikten sonra baştan değil kaldığı yerden devam eder → sağlamlık ve kontrol.
  • ReAct mimarisi: START → Agent ⇄ Tools → END. Ajan düşünür, gerekirse araç çağırır, sonucu değerlendirir, yeterli bilgi toplayınca cevap verir.
  • Chain mimarisi: Adımlar sırayla çalışır (ör. bilgi topla → metni yaz → kontrol et → paylaş).
  • Router mimarisi: İsteğe göre uygun bir yol seçilir (ör. "şifremi unuttum" → teknik destek ajanı).
  • Uzman ajan fikri: Bir işi tek LLM'e yaptırmak yerine her adım için ayrı rol/sistem mesajı ve ayar (temperature) kullanan "uzman" ajanlar → daha iyi sonuç.
  • Temperature: Rastgelelik. 0 = kararlı, kesin (SQL üretimi); ~0.7 = daha serbest (açıklama metni).
  • reasoning_effort="none": Modelin düşünme (reasoning) adımını kapatır; hocaya göre GPT-6 Luna'da temperature kullanabilmek için gerekli.
  • input_schema / output_schema: Grafın dışarıdan ne alıp ne döndüreceğini sınırlar; iç state daha geniş olabilir.
  • Structured output (with_structured_output): Model çıktısını bir Pydantic şemasına (ör. Literal["records","insurance"]) zorlar; router kararının iki değerden biri olmasını garanti eder.
  • Retriever: Sorguyu embedding'e çevirir → vektör DB'de arar → en benzer k belgeyi getirir (varsayılan 4; derste k=2).

Akış / mimari

Ajan seviyeleri – 3. seviye (asistan):

Dosyaları inceler → Hatayı bulur → Çözüm önerir → Onay ister → Değişikliği uygular

4. seviye (çoklu ajan):

"Websitesi yap" → Yönetici ajan → [Backend | Frontend | QA Tester | Technical Writer] → geri bildirim döngüsü → Nihai cevap

ReAct (LangGraph):

START → Agent ⇄ Tools
          ↓
         END

LangGraph'ta her zaman sıra:

State tanımla → Model tanımla → Düğüm fonksiyonları → add_node → add_edge / add_conditional_edges → compile(checkpointer=...) → invoke(input, config)

Chain (4_chain):

START → generate_sql (sql_model, T=0) → explain_sql (explain_model, T=0.7) → END

Router (5_router):

START → router ──records──→ retrieve_records ───┐
               └─insurance→ retrieve_insurance ─┴→ generate_answer → END

2) LangGraph: state, düğüm, bellek (3_langgraph.ipynb)

class State(TypedDict):
    messages: Annotated[list, add_messages]
  • messages bir liste; add_messages yeni mesajları ekler. Annotated = tip + güncelleme kuralı.
builder = StateGraph(State)                 # grafın iskeleti, hafızası State
model = ChatOpenAI(model="gpt-6-luna")      # ajanın beyni

def chatbot(state: State):
    response = model.invoke(state["messages"])   # tüm geçmiş modele gider
    return {"messages": [response]}              # cevap state'e eklenir

builder.add_node("chatbot", chatbot)        # ("düğüm adı", fonksiyon)
builder.add_edge(START, "chatbot")
builder.add_edge("chatbot", END)
graph = builder.compile()                   # derle

checkpointer = InMemorySaver()
graph = builder.compile(checkpointer=checkpointer)   # bellekli derleme

config = {"configurable": {"thread_id": "conversation-1"}}
result = graph.invoke({"messages": [HumanMessage(content="Merhaba, benim adım Evren.")]}, config=config)
result = graph.invoke({"messages": [HumanMessage(content="Benim adım ne?")]}, config=config)  # → "Adın Evren."
  • config olmadan bellekli graf hangi thread'e yazacağını bilemez; her çağrıda verilmeli.
  • config_2 (farklı thread) ile aynı soru → "bilmiyorum".
snapshot = graph.get_state(config)
for message in snapshot.values["messages"]:
    print(message.type, ":", message.content)
  • Thread'in tüm geçmişini (metadata ve token bilgileriyle) okur; döngü yalnızca tip:içerik yazdırır.

Kısa yol: StateGraph(MessagesState); MessagesState, elle yazılan State sınıfının hazır hâli.

3) Chain (4_chain.ipynb)

sql_model     = ChatOpenAI(model="gpt-6-luna", reasoning_effort="none", temperature=0)
explain_model = ChatOpenAI(model="gpt-6-luna", reasoning_effort="none", temperature=0.7)
  • Aynı model, iki farklı "kişilik": kesin SQL / daha serbest açıklama.
class State(MessagesState):
    user_query: str
    sql_query: str
    sql_explanation: str

class ChainInput(TypedDict):  user_query: str
class ChainOutput(TypedDict): sql_query: str; sql_explanation: str
  • İç state geniş, dış arayüz dar: kullanıcı yalnızca user_query verir, yalnızca SQL + açıklama alır.
def generate_sql(state: State) -> dict:
    question = HumanMessage(state["user_query"])
    res = sql_model.invoke([SQL_PROMPT, *state["messages"], question])  # sistem rolü + geçmiş + soru
    return {"sql_query": res.text, "messages": [question, res]}         # iki alan birden güncellenir

def explain_sql(state: State) -> dict:
    instruction = HumanMessage(
    f"Kullanıcının sorusu: {state['user_query']}\n\n"
    f"Üretilen sorgu:\n{state['sql_query']}\n\n"      # 1. düğümün çıktısı state'ten okunur
    f"Bu sorgunun ne yaptığını açıkla." )
    res = explain_model.invoke([EXPLAIN_PROMPT, instruction])
    return {"sql_explanation": res.text, "messages": [res]}
  • Zincir mantığı: 2. düğüm, 1. düğümün state'e yazdığı alanı kullanır.
graph = StateGraph(State, input_schema=ChainInput, output_schema=ChainOutput)
graph.add_edge(START, "generate_sql"); graph.add_edge("generate_sql", "explain_sql"); graph.add_edge("explain_sql", END)
display(Image(graph.compile().get_graph().draw_mermaid_png()))   # mimariyi çiz

DATABASE_SCHEMA = """
Table: sales
Columns:
- product_name TEXT
- sales_amount NUMERIC
"""
SQL_PROMPT = SystemMessage(f"""... Use ONLY the following schema. Do not invent tables or columns:
{DATABASE_SCHEMA}""")

Hocanın vurguları & pratik kurallar

  • AI mühendisi genelde model eğitmez, sıfırdan araç yazmaz; hazır LLM ve araçları API ile kullanır. API anahtarı yönetimi (.env + python-dotenv) temel beceridir.
  • Araç / düğüm fonksiyonlarının adı ve docstring'i çok önemli; ajan bunlara bakarak karar verir. Mümkünse İngilizce yazın.
  • Tip ipuçları ve şemalar (TypedDict, Literal, Pydantic, input/output schema) uygulamanın patlamasını önler, ajanı kontrol altında tutar.
  • LangGraph'ta sıra hep aynı: düğümleri oluştur → kenarları oluştur → bağla → derle.
  • Basit ajan için LangChain, döngü/hafıza/dallanma gerekiyorsa LangGraph.
  • Uzman ajanlar: her adıma ayrı rol (sistem mesajı) ve ayrı temperature.
  • Kesin çıktı (SQL, kod) → temperature 0; serbest metin → ~0.7.
  • Text-to-SQL'de veritabanı şemasını mutlaka verin ve "tablo/sütun uydurma" deyin; yoksa model varsayım yapar.
  • RAG cevabında "yalnızca bağlamı kullan, bilgi yoksa söyle" sistem talimatı → halüsinasyonu azaltır.
  • Basit uygulamada InMemoryVectorStore; büyüdükçe Chroma/FAISS, kompleks projede Pinecone/Qdrant; konuşma belleği için PostgreSQL/MySQL; Supabase'de metin + metadata + embedding birlikte tutulur.
  • Hazır sohbet araçları (Claude, ChatGPT) aynı işi yapar ama çok token harcar ve esnek değildir; kendi sistemini kurmak kontrolü size verir.
  • Yerel model önerisi: Qwen ~27B (ve 35B) iyi; 0.8B–2B gibi küçük modeller araç çağırmayı bile güvenilir yapamıyor.
  • VRAM kaba hesap: parametre(B)/2 + bunun ~¼'ü → 27B ≈ 18–19 GB. Yetmezse RAM'e taşar ama yavaşlar.
  • İyi bağlam (context) verirseniz modeller çok iyi sonuç verir; asıl fark modeli verimli kullanabilmektir (bootcamp'in amacı).
  • Kariyer: Tek kişinin frontend/backend/DevOps işlerini yapay zekâyla yapabildiği bir döneme giriliyor ("tek kişilik şirket"). Çok proje yap → CV'de göster. Final projesi kendi alanınızda bir RAG/ajan projesi olsun; basit başlayıp derslerle büyütün (ör. RAG → agentic RAG). Arayüz için Streamlit (kompleks ise Next.js).
  • Ödev (duyurulan): Chain (text-to-SQL) ve router uygulamalarını Streamlit arayüzüne çevirmek.

Kendini test et

  1. Chatbot ile ajan arasındaki temel fark nedir?
Cevap

Chatbot girdiye doğrudan çıktı üretir. Ajan ise görevi alır, düşünür, plan yapar, gerektiğinde araç kullanır ve görevi tamamlar; dış dünyada aksiyon alabilir.

  1. AI sistemlerinin 3. ve 4. seviyesini ayıran özellik nedir?
Cevap
  1. seviye (asistan) araç kullanır ama önemli kararlarda insandan onay ister (ör. Copilot). 4. seviye (agent) görevi alt görevlere bölüp alt ajanlara dağıtır, geri bildirim döngüsüyle süreci kendisi yönetir.
  1. Bir Python fonksiyonu LangChain aracına nasıl çevrilir ve ajan bu aracı neye bakarak seçer?
Cevap

@tool dekoratörüyle. Ajan aracı fonksiyon adına, tip ipuçlarına ve özellikle docstring açıklamasına bakarak seçer.

  1. Annotated[list, add_messages] ne işe yarar?
Cevap

messages alanının liste olduğunu ve yeni mesajların üzerine yazılmak yerine listeye eklenmesi gerektiğini belirtir. Konuşma geçmişi bu sayede birikir. MessagesState bunu hazır sunar.

  1. Checkpointer eklendiği hâlde ajan adınızı hatırlamıyorsa olası iki sebep nedir?
Cevap

(a) invoke çağrısında config (thread_id) verilmemiş ya da farklı bir thread_id kullanılmıştır; (b) graf checkpointer'sız derlenmiş bir sürümle çağrılıyordur.

  1. LangGraph'ın, hata durumunda normal bir programa göre avantajı nedir?
Cevap

Her adımın sonucu state'te kaydedildiği için hata düzeltildikten sonra baştan değil kaldığı yerden devam edebilir. Bu sağlamlık ve kontrol sağlar.

  1. Chain uygulamasında neden iki ayrı model nesnesi (sql_model, explain_model) kullanıldı?
Cevap

Her biri ayrı bir alanda uzman ajan olsun diye: SQL için temperature 0 (kesin), açıklama için 0.7 (daha serbest). Ayrıca her birine farklı sistem mesajı (rol) verildi.

  1. input_schema ve output_schema neden verildi?
Cevap

Grafın dışarıdan yalnızca user_query almasını ve yalnızca sql_query + sql_explanation döndürmesini sağlamak, yani girdi ve çıktıyı kontrol altında tutup modelin "kafasına göre" alan üretmesini önlemek için.

  1. Router uygulamasında router düğümü ile select_retriever fonksiyonunun görev farkı nedir?
Cevap

router bir düğümdür: LLM'e (structured output ile) soruyu sınıflandırtır ve state'e domain yazar. select_retriever ise düğüm değildir; add_conditional_edges'e verilen yön fonksiyonudur ve domain değerini gidilecek düğümün adına çevirir.

  1. Router'da with_structured_output(RouteDecision) kullanılmasaydı ne riski olurdu?
Cevap

Model serbest metin döndürebilir ("Bu soru sigortayla ilgili görünüyor…"). domain "records" ya da "insurance" dışında bir değer olur ve yönlendirme bozulurdu. Literal şeması kararı iki değerle sınırlar.
