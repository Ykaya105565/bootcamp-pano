08 · Day04 – Vektör Veri Tabanları

Bu derste ne var: Anahtar kelime araması (keyword search) ile anlamsal arama (semantic search) arasındaki fark üç uygulamayla gösterildi: SQLite'ta LIKE ile kelime araması, Sentence Transformers ile yerel anlamsal arama, OpenAI embedding'leri + FAISS ile ilk vektör veri tabanı. Teorik tarafta yapılandırılmış/yapılandırılmamış veri, SQL'in vektör saklamadaki sınırları, vektör DB'lerin ek özellikleri (indeksleme, yaklaşık arama, sparse saklama), hibrit yaklaşım ve doğru vektör DB seçimi ele alındı.

Ana kavramlar

  • Embedding (gömme vektörü) — Metin, görsel, ses gibi verinin sayısal vektör temsili. Neden önemli: Anlamca yakın veriler vektör uzayında yakın düşer; böylece "anlama göre" arama ve karşılaştırma yapılabilir.
  • Statik embedding — Her kelimeye tek, sabit bir vektör (Word2Vec). Sorun: Çok anlamlı kelimeleri ("Apple": şirket mi meyve mi) ayırt edemez.
  • Bağlamsal embedding (contextual embedding) — Transformer tabanlı; aynı kelimenin vektörü cümleye göre değişir. Neden önemli: Modern embedding modellerinin (Sentence Transformers, OpenAI) temeli.
  • Word2Vec vs Doc2Vec — Word2Vec her kelimeyi, Doc2Vec her dokümanı vektöre çevirir.
  • Cümle embedding'i (ortalama/pooling) — Token embedding'lerinin ortalaması alınarak cümlenin tek vektörü elde edilir. Neden önemli: model.encode(cümle) bize token değil cümle vektörü döndürür.
  • Yapılandırılmış veri (structured data) — Tablo halinde, sütunları/anahtarları belli veri (Excel, SQL tablosu). SQL DB'leri bunda çok güçlü.
  • Yapılandırılmamış veri (unstructured data) — Görüntü, metin, PDF, ses, video, IoT sensör verisi. Klasik DB'de saklansa bile anlamsal arama yapılamaz.
  • Anahtar kelime araması (keyword search) — Bire bir kelime eşleşmesi (LIKE '%...%'). Eş anlamlıları kaçırır.
  • Anlamsal arama (semantic search) — Sorgu ve dokümanlar embedding'e çevrilir, en benzer vektörler getirilir. "araba bozuldu" → "Otomobilim marş basmıyor".
  • Vektör veri tabanı (vector database) — Embedding'leri saklayan, benzerlik aramasını indekslerle hızlı yapan DB. Kullanım: anlamsal arama, RAG, görsel benzerlik araması.
  • Benzerlik ve mesafe ölçüleri — Kosinüs benzerliği (büyük = daha benzer), Öklid / L2 mesafesi (küçük = daha yakın), k-en yakın komşu (k-NN).
  • LSH / HNSW — Vektör DB'lerin indeksleme teknikleri; benzer vektörleri yakın yerlere yerleştirerek aramayı hızlandırır.
  • Yaklaşık en yakın komşu araması (approximate search) — Kesin değil, yeterince iyi sonucu hızlı bulur. RAG'de "en ilgili birkaç doküman" için yeterli.
  • Sparse vs dense vektör — Sparse: çoğu değer sıfır (ör. 30.000 boyutlu sözlük vektörü); dense: düşük boyutlu, çoğu değeri sıfırdan farklı (embedding'ler). Sparse vektörler indices + values ile verimli saklanır.
  • Metadata ve hibrit arama — Vektör benzerliği + SQL tarzı filtreler (kategori, tarih, etiket) birlikte. Örnek: PostgreSQL + pgvector.
  • FAISS — Meta'nın vektör arama kütüphanesi; küçük deneyler ve RAG prototipleri için. IndexFlatL2 = L2 mesafesiyle düz (tam/brute-force) arama.

Akış / mimari

Anahtar kelime vs anlamsal arama

Keyword:   sorgu metni → SQL LIKE '%kelime%' → yalnızca birebir geçen satırlar
Semantic:  sorgu metni → embedding → benzerlik (cosine / L2) → en yakın k doküman

Vektör DB ile arama (bu dersteki FAISS akışı)

text_chunks → get_embedding() → np.array → float32 → faiss.IndexFlatL2(dim) → index.add()
sorgu → get_embedding() → float32 → reshape(1, -1) → index.search(q, k) → (distances, indices) → text_chunks[i]

RAG'deki yeri (gelecek ders)

PDF / doküman → parçalama (chunking) → embedding → vektör DB'de sakla → kullanıcı sorusu → en ilgili chunk'lar → LLM

Hibrit sorgu (çizimden)

"2024 sonrası, bilim kategorisinde, yapay zekâ ile ilgili en iyi 10 doküman"
 ├─ "yapay zekâya benzeyen"       → vektör benzerlik araması
 ├─ category = 'science'          → metadata filtresi
 ├─ publish_date > '2024-01-01'   → tarih filtresi
 └─ ilk 10                        → sıralama + limit

2) SQLite ile anahtar kelime araması (01-Keyword-Search.ipynb)

import sqlite3
conn = sqlite3.connect(":memory:")
cur = conn.cursor()
cur.execute("CREATE TABLE dokumanlar (id INTEGER PRIMARY KEY, icerik TEXT)")
cur.executemany("INSERT INTO dokumanlar (icerik) VALUES (?)", kayitlar)
cur.execute("SELECT icerik FROM dokumanlar WHERE icerik LIKE '%araba bozuldu%'")
sonuc = cur.fetchall()
print("Bulunan satır:", len(sonuc))
  • sqlite3 Python ile birlikte gelir; kurulum gerekmez.
  • ":memory:" → veri tabanı RAM'de; kernel kapanınca silinir.
  • cursor() → SQL komutlarını çalıştıracak imleç.
  • CREATE TABLE → id birincil anahtar (benzersiz), icerik metin.
  • executemany(..., kayitlar) → listedeki her tuple için bir INSERT; ? yer tutucusu SQL enjeksiyonuna karşı da güvenlidir. Kayıtlar ("metin",) şeklinde tek elemanlı tuple olmalı.
  • LIKE '%araba bozuldu%' → 0 satır; LIKE '%araba%' → 1 satır (sadece "Yeni arabamı…").

3) Sentence Transformers ile anlamsal arama (02-Semantic-Search.ipynb)

from sentence_transformers import SentenceTransformer
model = SentenceTransformer("paraphrase-multilingual-MiniLM-L12-v2")
metinler = [k[0] for k in kayitlar]
vektorler = model.encode(metinler)
print(vektorler.shape)          # (5, 384)
sorgu = "araba bozuldu"
sorgu_vek = model.encode(sorgu)
skorlar = model.similarity(sorgu_vek, vektorler)[0]
for i in np.argsort(-skorlar)[:3]:
    print(f"{skorlar[i]:.3f} {metinler[i]}")
  • Çok dilli (multilingual) küçük model → Türkçe için; yerel çalışır, API gerekmez.
  • [k[0] for k in kayitlar] → tuple'lardan düz metin listesi.
  • encode → her cümle için 384 boyutlu bağlamsal embedding.
  • Sorgu da aynı modelle encode edilmeli.
  • similarity → benzerlik skoru; büyük = daha benzer. [0] tek sorgunun satırını alır.
  • np.argsort(-skorlar) → eksiyle çarpıp büyükten küçüğe sıralama; [:3] ilk üç.
  • Sonuç: 1) "Otomobilim marş basmıyor…" 2) "Aracım çalışmıyor…" 3) "Yeni arabamı…".

4) OpenAI embedding + FAISS (03-Vector-DB.ipynb)

from dotenv import load_dotenv
load_dotenv()
from openai import OpenAI
client = OpenAI()
model = "text-embedding-3-small"

def get_embedding(text):
    response = client.embeddings.create(input=text, model=model)
    return response.data[0].embedding
  • load_dotenv() → .env içindeki OPENAI_API_KEY'i ortama yükler (ortam değişkeni zaten tanımlıysa gerekmez).
  • OpenAI() → anahtarı ortamdan otomatik okur.
  • text-embedding-3-small → 1536 boyutlu vektör; large daha büyük boyut üretir.
  • response.data[0].embedding → tek girdinin vektörü (Python listesi).
document_embeddings = np.array([get_embedding(t) for t in text_chunks]).astype("float32")
index = faiss.IndexFlatL2(document_embeddings.shape[1])
index.add(document_embeddings)
print(index.ntotal)                              # 6
query_embedding = np.array(get_embedding(query)).astype("float32")
distances, indices = index.search(query_embedding.reshape(1, -1), k)
  • .astype("float32") → numpy varsayılanı float64; FAISS float32 ister.
  • IndexFlatL2(dim) → L2 (Öklid) mesafesiyle tam arama yapan indeks; dim = 1536.
  • index.add → vektörleri indekse ekler; ntotal toplam vektör sayısı.
  • reshape(1, -1) → (1536,) → (1, 1536); FAISS her zaman 2B (sorgu sayısı × boyut) bekler.
  • search(q, k) → en yakın k vektörün mesafeleri ve indisleri; küçük mesafe = daha yakın.
  • Sonuç ("Menekşeler ne renktir?"): Menekşeler mavidir → Gökyüzü mavidir → Dondurma lezzetlidir → Güneş parlıyor → Güller kırmızıdır.

5) Hibrit sorgu – PostgreSQL + pgvector (çizimden)

SELECT title, category, publish_date, views,
       embedding <=> :query_vector AS distance
FROM documents
WHERE category = 'science' AND publish_date > '2023-01-01'
ORDER BY distance ASC
LIMIT 10;
  • <=> → pgvector'ün mesafe operatörü (Not: pgvector'de <=> kosinüs mesafesi, <-> L2 mesafesidir).
  • WHERE → metadata filtreleri; ORDER BY distance ASC LIMIT 10 → en yakın 10.

Hocanın vurguları & pratik kurallar

  • Klasik veri tabanlarını küçümsemeyin: SQL'i en azından temel seviyede bilmek şart; uygulamaların çoğu hâlâ klasik DB kullanıyor.
  • Her proje için ayrı ortam (uv) → sürüm çakışması olmaz.
  • Araç bağımlılığı olmasın: uv sorun çıkarırsa Conda, o da olmazsa pip. Hepsini bilmek fayda sağlar.
  • Türkçe metin için çok dilli embedding modeli seçin.
  • Embedding'e çevirmenin iki yolu: OpenAI (API, ücretli) veya Sentence Transformers (açık kaynak, lokal).
  • Yapay zekâ uygulamalarında yaklaşık sonuç yeterli — vektör DB'lerin hız avantajı buradan gelir.
  • Skor yönüne dikkat: benzerlik (cosine) → büyük iyi; mesafe (L2) → küçük iyi.
  • Vektör DB seçimi (çizimden):
  • Küçük deneyler / RAG prototipi → FAISS (Meta) veya Chroma (Python ile hızlı başlangıç, yerel RAG için ideal).
  • Zaten PostgreSQL varsa → pgvector; MongoDB varsa → MongoDB Atlas Vector Search. Redis için RediSearch.
  • Büyük ölçek / kurumsal → Qdrant, Weaviate, Milvus (açık kaynak, lokal + bulut), Pinecone (yalnız bulut).
  • Gerçek hayatta sadece vektör yetmez: tarih, kategori, etiket gibi metadata'yı da saklayıp hibrit arama yapın.
  • Ortam değişkeni adı büyük harf: OPENAI_API_KEY.
  • Ders öncesi ortamı (klasör + kernel + "Merhaba Dünya") hazırlayıp gelin.

Kendini test et

  1. Anahtar kelime araması "araba bozuldu" sorgusunda neden hiç sonuç döndürmedi, LIKE '%araba%' neden sadece bir satır buldu?
Cevap

Keyword search birebir metin eşleşmesi arar. "araba bozuldu" ifadesi hiçbir kayıtta aynen geçmiyor. "araba" sadece "Yeni arabamı…" cümlesinde geçiyor; "aracım", "otomobilim", "vasıtam" gibi eş anlamlılar yakalanamıyor.

  1. Statik ve bağlamsal embedding arasındaki fark nedir? "Apple" örneğiyle açıklayın.
Cevap

Statik embedding'de (Word2Vec) "Apple"ın tek bir vektörü vardır; şirket mi meyve mi ayrılamaz. Bağlamsal (Transformer tabanlı) embedding'de vektör cümleye göre değişir: "I ate an apple…" ile "Apple released a new iPhone." farklı temsil edilir.

  1. model.encode(metinler) çıktısının şekli (5, 384); bu sayılar ne anlama geliyor ve cümle vektörü nasıl elde ediliyor?
Cevap

5 = cümle sayısı, 384 = her cümlenin embedding boyutu. Token embedding'leri (bağlamsal olarak) hesaplanır, ardından ortalamaları alınarak tek bir cümle vektörü elde edilir.

  1. np.argsort(-skorlar)[:3] satırında neden eksi işareti var?
Cevap

argsort küçükten büyüğe sıralar. Benzerlik skorunda büyük değer daha iyidir; eksiyle çarparak büyükten küçüğe sıralama elde edilir ve ilk üç en benzer sonuç alınır.

  1. FAISS'e veri eklemeden önce neden .astype("float32") yapıyoruz, sorguda neden reshape(1, -1) kullanıyoruz?
Cevap

FAISS float32 ile çalışır, numpy ise varsayılan olarak float64 üretir. search iki boyutlu (sorgu sayısı × boyut) girdi bekler; tek sorgu vektörü (1536,) olduğundan (1, 1536) yapılır.

  1. IndexFlatL2 sonuçlarında küçük değer mi büyük değer mi daha iyi? model.similarity'de durum ne?
Cevap

L2 bir mesafedir: küçük = daha yakın. similarity bir benzerlik skorudur (Sentence Transformers'da varsayılan kosinüs): büyük = daha benzer.

  1. SQL veri tabanına embedding'i VECTOR(768) / FLOAT[] sütunu olarak koymak neden tek başına yetmez? Eklenti yaklaşımının dezavantajları nelerdir?
Cevap

SQL DB sayı listesinin anlamını bilmez, sadece sayıları görür; benzerlik araması yapamaz. Eklentiyle genişletilirse performans sorunu, vektör işlemlerini iyi yapamama ve vektör sayısı arttıkça ölçeklenebilirlik sorunu ortaya çıkar.

  1. Vektör veri tabanlarının klasik DB'lere göre sunduğu dört ek özellik nedir?
Cevap

(1) LSH/HNSW gibi indekslerle yüksek boyutlu veride hızlı arama, (2) kosinüs, Öklid, k-NN gibi vektör işlemlerini doğrudan destekleme, (3) yaklaşık aramayı hızlı yapma, (4) sparse vektörleri verimli saklama.

  1. [0, 0, 0.8, 0, 0, 0.3, 0] vektörünün sparse gösterimi nedir, neden avantajlıdır?
Cevap

indices = [2, 5], values = [0.8, 0.3]. Sıfırlar saklanmadığı için bellek ve işlem tasarrufu sağlar.

  1. Şirketiniz zaten PostgreSQL kullanıyor ve "2024 sonrası, bilim kategorisinde, yapay zekâ ile ilgili 10 doküman" sorgusu gerekiyor. Hangi yaklaşımı ve aracı seçersiniz?
Cevap

Hibrit yaklaşım: PostgreSQL + pgvector. Vektör benzerliği (embedding <=> :query_vector) ile metadata filtreleri (category, publish_date) birlikte, ORDER BY distance LIMIT 10.
