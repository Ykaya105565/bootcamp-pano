09 · Day05 - RAG Giriş

Bu derste ne var: Geçen dersin tekrarı (veri türleri, embedding, vektör veritabanları) ve Kahoot'un ardından RAG'ın ne olduğu, neden gerektiği ve fine-tuning'den farkı anlatıldı. RAG pipeline'ının 3 aşaması (indexing → retrieval → generation) çizildi, ardından LangChain ile uçtan uca bir RAG uygulaması kuruldu: metin yükleme → Document → RecursiveCharacterTextSplitter ile chunking → OpenAI embedding + Chroma → retriever → ChatPromptTemplate → LLM → @chain ile kaynak gösteren QA fonksiyonu.

Kayıt notu: ≈02:00–02:33 arası videoda ses yok (mola + kayıt boşluğu). Embedding ve Chroma'ya kaydetme adımı bu aralıkta kaldığı için indexing.ipynb'den tamamlandı; o kısımlardaki açıklamalar hocanın değil, "Not:" olarak benim eklememdir.

Ana kavramlar

  • Yapılandırılmış veri (structured): Tablo, sütun ve satırlardan oluşur; SQL veritabanlarında saklanır. Önemi: Analizi kolaydır; LLM'in "anlamadığı" karmaşık verilerle karşılaştırma noktası.
  • Yapılandırılmamış veri (unstructured): Görüntü, metin, ses, video; NoSQL (ör. MongoDB) ile saklanır. Önemi: RAG'ın işlediği PDF/metin dokümanları bu sınıftadır.
  • Embedding: Girdileri sayısal temsillere (vektörlere) çevirme. Önemi: LLM yalnızca sayısal veriden anlar; semantik aramanın temeli.
  • Keyword arama vs. semantik arama: Keyword birebir kelime eşleşmesine, semantik arama anlam benzerliğine bakar ("araba bozuldu" ≈ "aracım çalışmıyor"). Önemi: RAG'ın retrieval adımı semantik aramadır.
  • pgvector: PostgreSQL'e vektör sütunu ve HNSW/IVFFlat indeksleri ekleyen eklenti; semantik ve hibrit (vektör + SQL) sorgu sağlar. Önemi: Şirket zaten PostgreSQL kullanıyorsa en pratik yol. Dezavantajı: çok büyük veride yavaşlar.
  • Vektör veritabanı: Vektör benzerlik aramasına özel DB. Küçük ölçek: FAISS (Meta, kütüphane, in-memory), Chroma. Büyük ölçek: Qdrant, Weaviate, Milvus, Pinecone (Pinecone yalnız bulut).
  • Fine-tuning: Base/foundation modeli alana özgü veriyle yeniden eğitmek; parametreler (ağırlıklar) güncellenir. Önemi: Masraflı, zaman alıcı, uzmanlık ister.
  • Parametre: Sinir ağındaki nöronlar arası bağlantıların ağırlıkları (weights).
  • RAG (Retrieval-Augmented Generation): 2020'de çıktı. İlgili veriyi getir (retrieval) → promptu/bağlamı zenginleştir (augmented) → cevabı üret (generation). Parametreler eğitilmez. Önemi: Ucuz, veriler lokalde kalabilir, güncel/özel bilgi verir, halüsinasyonu azaltır; şirketler genelde bunu tercih eder. Hocaya göre "AI engineer'ın Hello World'ü".
  • Context: Modele soru ile birlikte verilen bilgi. "Context her şeydir."
  • Chunk / chunking: Dokümanı küçük parçalara bölme. Önemi: Token maliyetini ve context uzunluğunu azaltır; modele sadece ilgili parça gider.
  • Chunk size: Parça uzunluğu (karakter). Çok büyük → gereksiz bilgi; çok küçük → doğru bilgi yakalanamaz.
  • Chunk overlap: Ardışık parçalar arasındaki ortak bölüm. Önemi: Anlam bütünlüğünü korur.
  • RecursiveCharacterTextSplitter: Metni doğal yerlerden böler: önce paragraf → satır → boşluk (→ karakter).
  • Document (LangChain): page_content + metadata. Önemi: Cevabın kaynağını (dosya, parça, sayfa) takip etmeyi sağlar.
  • Retriever (as_retriever): Sorguyu embedding'e çevirir, vektör DB'deki embedding'lerle karşılaştırır, en benzer k dokümanı döndürür. Varsayılan k=4.
  • ChatPromptTemplate: system/human mesajlarından oluşan, {değişken} alanları olan prompt şablonu.
  • Temperature: 0 → deterministik, kesin; 1'e yaklaştıkça yaratıcı/rastgele.
  • Pipe (|) ve @chain: LangChain'de adımları zincirleme bağlama; @chain dekoratörü normal bir Python fonksiyonunu zincir (Runnable) gibi çalıştırır.
  • LangChain ekosistemi: LangChain Core (prompt/context araçları), LangGraph (ajanlar), LangSmith (observability). Alternatifler: LlamaIndex (RAG öncelikli), Haystack (deepset; kurumsal destek var, topluluk az).

Akış / mimari

Genel yol haritası (derslerin sırası):

LLM → prompt engineering → context engineering → embedding → vektör DB → RAG

RAG pipeline — 3 aşama:

1) INDEXING   : Dokümanları yükle → chunk'lara böl → embedding'e çevir → vektör DB'de sakla
2) RETRIEVAL  : Kullanıcı sorusu → embedding → vektör DB'de benzerlik araması → Top-K chunk (sıralı)
3) GENERATION : {context = Top-K chunk} + {question} → prompt template → LLM → cevap

Bu dersin kod akışı (indexing.ipynb):

Path("docs/test.txt") → read_text → Document(page_content, metadata)
  → RecursiveCharacterTextSplitter(600, 120, add_start_index) → documents (chunk listesi)
  → OpenAIEmbeddings("text-embedding-3-small")
  → Chroma.from_documents(... persist_directory="./chroma_db", collection_name="antik_yunan")
  → vector_store.as_retriever(k=3)
  → format_docs(docs) → ChatPromptTemplate(system+context, human+question)
  → ChatOpenAI(temperature=0) → cevap (+ kaynak dokümanlar)

Fine-tuning vs RAG:

Fine-tuning : Devasa veri → pre-training → Base model → (+ alana özgü veri) → Fine-tuned LLM ⇄ kullanıcı
RAG         : Base model sabit → (sorguya göre vektör DB'den getirilen context) → cevap
Fine-tuning RAG
Parametreler Yeniden eğitilir Eğitilmez
Maliyet Yüksek (güçlü GPU) Düşük
Süre Uzun (gün mertebesi) Hızlı
Uzmanlık Gerekir Daha az
Güncel/özel veri Yeniden eğitim gerekir Dokümanı ekle, yeter

2) Dokümanı yükleme ve Document'e çevirme

from pathlib import Path 
path = Path("./docs/test.txt")
text = path.read_text(encoding="utf-8")

from langchain_core.documents import Document
raw_documents = [
    Document(
    page_content=text,
    metadata={"source": "docs/test.txt"},
    )
]
  • Path(...): Yolu işletim sisteminden bağımsız bir nesneye çevirir (yol ayırıcı hatalarını önler).
  • encoding="utf-8": Türkçe karakterlerin bozulmaması için.
  • Document(page_content=..., metadata=...): Metni LangChain'in standart yapısına koyar; source metadata'sı cevabın kaynağını izlemek için.
  • Liste olmasının nedeni: splitter'lar ve vektör DB'ler doküman listesi bekler; ileride birden çok dosya eklenebilir.

3) Chunking

from langchain_text_splitters import RecursiveCharacterTextSplitter 

text_splitter = RecursiveCharacterTextSplitter(
    chunk_size=600,
    chunk_overlap=120,
    add_start_index=True  
)
documents = text_splitter.split_documents(raw_documents)
len(documents)
  • chunk_size=600: Bir parça en fazla ~600 karakter (kısa/orta metin için).
  • chunk_overlap=120: 600'ün %20'si; parça sınırında bağlam kopmasın diye.
  • add_start_index=True: Her chunk'ın metadata'sına start_index (orijinal metinde başladığı karakter) eklenir; kaynak gösterirken işe yarar.
  • split_documents: Metadata'yı koruyarak her Document'i chunk'lara böler; sonuç yine Document listesi.
  • len(documents): Kaç chunk oluştuğunu verir (index out of range almamak için).
  • Derste: paragraflar 600'den kısa olduğu için her paragraf ayrı chunk oldu (ilk chunk 411 karakter) ve overlap oluşmadı.

5) Retriever

retriever = vector_store.as_retriever(search_kwargs={"k": 3})
docs = retriever.invoke("Antik Yunan'da kadınların toplumdaki rolü nedir?")
len(docs)   # 3
  • as_retriever(): Vektör DB'yi "soru al → embed et → benzerlik ara → doküman döndür" yapan bir nesneye çevirir.
  • search_kwargs={"k": 3}: Varsayılan 4 yerine 3 chunk döndür (context şişmesin).
  • .invoke(soru): LangChain Runnable arayüzüyle çalıştırma.

6) Prompt şablonu ve doküman biçimlendirme

from langchain_core.prompts import ChatPromptTemplate

SYSTEM_PROMPT = ( 
    "Answer the question based only on the following context. " 
    "If the answer isn't in the context, say you don't know.\n\n" 
    "Context:\n{context}" )

prompt = ChatPromptTemplate([ 
    ("system", SYSTEM_PROMPT), 
    ("human", "{question}"), 
])
prompt.pretty_print()
prompt.input_variables   # ['context', 'question']

def format_docs(docs):
 return "\n\n".join(doc.page_content for doc in docs)
  • System prompt: "Sadece bağlama göre cevap ver; yoksa bilmediğini söyle" → halüsinasyonu engelleyen asıl kural.
  • {context}, {question}: Şablon değişkenleri; çalışma anında doldurulur.
  • pretty_print() / input_variables: Şablonu ve beklediği değişkenleri kontrol etmek için.
  • format_docs: Document listesinden sadece page_content'leri alıp aralarına boş satır koyarak tek bir düz metin yapar (metadata modele gitmez).

7) LLM ve zincir

from langchain_openai import ChatOpenAI
llm = ChatOpenAI(model="gpt-5.6-luna", temperature=0)

rag_chain = prompt | llm
response = rag_chain.invoke({"context": docs, "question": question})
print(response.content)
  • temperature=0: Kesin, tekrarlanabilir cevap.
  • prompt | llm: Prompt'un çıktısı LLM'in girdisi olur (pipeline).
  • Not: Burada context olarak docs listesi doğrudan verilmiş (format_docs uygulanmamış); şablon listeyi metne çevirdiğinde metadata da araya girer. Bir sonraki adımdaki qa fonksiyonu bunu format_docs ile düzeltir.

8) @chain ile tek fonksiyon + kaynaklar

from langchain_core.runnables import chain

@chain 
def qa_with_sources(question: str): 
    docs = retriever.invoke(question)              # 1) retrieval
    context = format_docs(docs)                    # 2) düz metin context
    formatted_prompt = prompt.invoke({             # 3) şablonu doldur
        "context": context, 
        "question": question 
    }) 
    answer = llm.invoke(formatted_prompt)          # 4) generation
    return {"answer": answer.content, "docs": docs}  # 5) cevap + kaynaklar

result = qa_with_sources.invoke("Antik Yunan'da günlük yaşam nasıldı?")
for doc in result["docs"]:
    print(doc.page_content); print(doc.metadata); print("-" * 50)

# RAG'in en kritik davranışı: bilmediğini bilmek
result = qa_with_sources.invoke("Antik Yunan'da hangi kripto paralar kullanılıyordu?")
print(result["answer"])
  • @chain: Fonksiyonu Runnable yapar → .invoke() ile çağrılır, diğer zincirlerle | ile birleştirilebilir.
  • "docs": docs döndürmek: Cevabın hangi chunk'lardan geldiğini (source, start_index — derste 0, 940, 2003) gösterir.
  • Kripto sorusu: Bağlamda yok → model "metinde yer almıyor / bilmiyorum" dedi.

Hocanın vurguları & pratik kurallar

  • Chunk size başparmak kuralı: kısa metin 300–600, makale/ders notu 600–1000, uzun metin 1000–2000 karakter. Projeye/metne göre seçin.
  • Overlap: chunk size'ın %10–20'si (600 → 60–120; 1000 → 100–200). Az → bağlantı kopar; çok → gereksiz tekrar.
  • Retriever k: Varsayılan 4; context şişmesin diye 2–3'e indirilebilir.
  • Vektör DB seçimi proje bazlı: "Bakkaldan ekmek almak için Ferrari'ye gerek yok." Küçük/prototip → FAISS, Chroma; büyük ölçek → Qdrant, Weaviate, Milvus, Pinecone; şirket PostgreSQL kullanıyorsa → pgvector. En büyük hata: ihtiyaca bakmadan en popüler/güçlü olanı seçmek.
  • RAG ölmez: Context window büyüse de context şişince cevap kalitesi düşer ve maliyet artar.
  • Şirketler RAG'ı tercih eder: Ucuz, veri lokalde kalabilir, yeniden eğitim yok.
  • Matematiği ezberlemeye gerek yok, ama teoriyi bilin: Mülakatlarda soruluyor; asıl iş problemi anlayıp doğru mimariyi kurmak.
  • Vibe coding uyarısı: Mimariyi baştan siz söyleyin (backend Python, frontend Streamlit vb.), önce plan yaptırın; kodu okuyup anlatabilmeli, hata çözebilmelisiniz. Çalışan şey ≠ ürün (güvenlik, yük, entegrasyon testleri).
  • Proje = CV: Özellikle yurt dışında projelere bakılıyor.
  • Yeni rol: Forward deployed engineer / AI solutions engineer — şirketin süreçlerini öğrenip yapay zekâya taşımak.
  • Gizlilik: Ucuz Çin modelleri cazip ama veri gönderiliyor; hassas veride maskeleme ya da lokal model düşünülmeli.
  • Model takibi: LMArena ve Artificial Analysis.

Kendini test et

  1. RAG'ın açılımı nedir ve her harf hangi adıma karşılık gelir?
Cevap

Retrieval-Augmented Generation. Retrieval: sorguyla ilgili veriyi vektör DB'den getir; Augmented: promptu/context'i bu veriyle zenginleştir; Generation: LLM cevabı üretir.

  1. Fine-tuning ile RAG arasındaki temel fark nedir? Şirketler neden genelde RAG'ı tercih eder?
Cevap

Fine-tuning'de modelin parametreleri (ağırlıkları) alana özgü veriyle yeniden eğitilir; RAG'da eğitilmez, bilgi sorgu anında context olarak verilir. RAG daha ucuz ve hızlıdır, uzmanlık/GPU gerektirmez, veriler lokalde kalabilir, güncel bilgiyi doküman ekleyerek verirsiniz.

  1. RAG pipeline'ının 3 aşamasını alt adımlarıyla sayın.
Cevap

1) Indexing: yükle → chunk'la → embed et → vektör DB'de sakla. 2) Retrieval: soruyu embed et → benzerlik araması → Top-K chunk. 3) Generation: context + soru → prompt → LLM → cevap.

  1. Neden tüm dokümanı doğrudan LLM'e vermiyoruz? "RAG öldü mü?" tartışmasına hocanın cevabı neydi?
Cevap

Çok token harcanır (maliyet), context şişer ve cevap kalitesi düşer. Context window'lar büyüse de bu iki sorun devam ettiği için RAG ölmez.

  1. 5.000 karakterlik ders notu için chunk_size ve overlap ne seçersiniz?
Cevap

Makale/ders notu kuralına göre chunk_size 600–1000 (ör. 800), overlap bunun %10–20'si (ör. 80–160).

  1. RecursiveCharacterTextSplitter metni hangi sırayla böler? Derste neden overlap oluşmadı?
Cevap

Önce paragraf, sonra satır, sonra boşluk (en son karakter). Derste paragraflar 600 karakterden kısa olduğu için her paragraf tek chunk oldu (ilki 411 karakter); paragraf sınırında kesildiği için overlap'a gerek kalmadı.

  1. Metni neden LangChain Document nesnesine çeviriyoruz? add_start_index=True ne ekler?
Cevap

Metadata'yı (ör. source) taşımak ve cevabın kaynağını takip etmek için. add_start_index=True her chunk'ın metadata'sına orijinal metindeki başlangıç karakter konumunu (start_index) ekler.

  1. vector_store.as_retriever(search_kwargs={"k": 3}) çağrıldığında invoke(soru) arka planda hangi üç işi yapar?
Cevap

Soruyu embedding'e çevirir, vektör DB'deki embedding'lerle benzerlik karşılaştırması yapar, en benzer 3 dokümanı döndürür. (k verilmezse varsayılan 4.)

  1. System prompt'taki "If the answer isn't in the context, say you don't know" satırı neden kritik? Derste nasıl test edildi?
Cevap

Modelin kendi bilgisiyle uydurmasını (halüsinasyon) engeller; RAG'ın "bilmediğini bilmek" davranışı. Dokümanda olmayan "Antik Yunan'da hangi kripto paralar kullanılıyordu?" sorusu soruldu, model bilginin metinde olmadığını söyledi.

  1. Küçük bir prototip, 5 milyon kayıtlı kurumsal sistem ve zaten PostgreSQL kullanan bir şirket için hangi vektör depolama çözümlerini önerirsiniz?
Cevap

Prototip: FAISS veya Chroma. Büyük kurumsal sistem: Qdrant, Weaviate, Milvus veya Pinecone (yalnız bulut). PostgreSQL kullanan şirket: pgvector eklentisi (hibrit vektör + SQL sorgu).
