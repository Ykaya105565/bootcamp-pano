Yapay zekâ uygulamalarının üç aşaması (≈00:21–00:28)

Hoca, bir önceki derste gördüklerini üç aşamada özetledi:

  1. LLM çağrısı (LLM call): En basit sistem. Tek bir LLM kullanılır, klasik chatbot gibi. ChatGPT ilk çıktığında böyle çalışıyordu. LLM, yapay zekâ uygulamasının "beyni"dir.
  2. Araç kullanan sistemler (tool use / function calling): Beyin hâlâ pasiftir; yalnızca eğitim verisinin kesildiği tarihe kadarki bilgiyi bilir. Daha güncel bilgi için dış dünyaya açılması gerekir; bunu araçlar (tools) ile yapar. LLM araca konuşur, ondan bilgi alır, bu bilgiyle cevap üretir. Örnekler: - Hesap makinesi: İlk LLM'ler çarpma işlemini düzgün yapamıyordu, çünkü bir sonraki token'ı tahmin eden olasılıksal modellerdi. Hesap makinesi aracı bağlanınca doğru cevap veriyor. - Web arama: Bugünkü gram altın ya da dolar kuru gibi güncel bilgiler; araç internetten bağlam (context) bulur, LLM'e verir. - Hava durumu: Hava durumu aracı sorgulanır, cevap LLM'e döner. Literatürde bu çalışma biçimine function calling (fonksiyon çağırma) deniyor.
  3. Ajan tabanlı (agentic) sistemler: Önceki sistemlerde LLM düşünmüyordu, düşünerek karar vermiyordu. Agentic sistemde uygulama düşünür, karar verir, gerekirse tekrar düşünür, araca tekrar gider, gelen cevaba göre yeniden plan yapar; nihai karara varınca sonucu döndürür. Ayrıca bilgiyi hafızaya alır ve aksiyona geçer (ör. "bana en ucuz bileti bul" → bulur, gerekirse satın alır). Hoca 2026'yı "agentic yılı" olarak niteledi; ChatGPT, Claude ve Gemini'nin arkasındaki sistem de bu.

Kullanılabilecek araç örnekleri: hesap makinesi, hava durumu, web search, veritabanları, dosya sistemleri, çeşitli API'ler, web servisleri.

MCP neden gerekli? (≈00:28–00:34)

  • Uygulamayı her araca bağlamak için ayrı entegrasyon kodu yazmak gerekiyor; her araç için ayrı kod yazmak uzun ve yorucu.
  • MCP, uygulamaları araçlara bağlamak için bir standart iletişim protokolü.
  • USB-C benzetmesi: 10–15 yıl önce her telefon markasının ayrı şarj girişi vardı; bir firmanın şarj aletini başka telefonda kullanamazdınız. USB-C ile tek standart geldi. MCP de aynı standardı yapay zekâ uygulamaları ile araçlar arasında sağlıyor.
  • Sinir sistemi benzetmesi: Uygulama bir vücutsa LLM beyindir; beyin karar verir ("elini oynat"), bu emrin ele ulaşması sinir sistemiyle olur. MCP de bu iletişimi sağlayan standart katmandır.
  • Önemli vurgu: MCP yapay zekâyı daha zeki yapmaz. MCP bir bağlantı ve iletişim katmanıdır.
  • M × N problemi: 3 yapay zekâ uygulaması (ör. AI Agent, AI IDE, AI Chat) ve 5 araç (GitHub, Slack, PostgreSQL, hava durumu API, Stripe) varsa, doğrudan bağlamak için 3 × 5 = 15 ayrı entegrasyon gerekir. Araya tek bir MCP katmanı koyunca her uygulama bu katmana, katman da araçlara bağlanır; tek bir standartla iş çözülür.
  • MCP'yi Anthropic geliştirdi (Claude'un şirketi). Önce sürüm 1, sonra sürüm 2 çıktı; derste kurulan mcp paketi sürümü 2.3.0. n8n gibi araçlar ve Supabase de MCP destekliyor; artık neredeyse her araçta MCP bağlantısı var.

Soru: MCP sadece Anthropic'in standardı mı, yoksa tüm sektörün mü? (Öğrenci, işlemci mimarilerinin zamanla AMD64 gibi ortak bir standarda yakınsamasını örnek verdi.) Cevap: Anthropic geliştirdi ama artık fiilen standart: OpenAI, Google ve diğer şirketler de kullanıyor. Benzer şekilde Google'ın geliştirdiği A2A (Agent2Agent) protokolü de standartlaşıyor. Model çağırırken ise OpenAI API formatı fiilen standart; açık kaynak modelleri (ör. Qwen) kullanırken de OpenAI uyumlu API ile client oluşturup response alıyoruz. Bağlantı standardı olarak da MCP kullanılıyor.

MCP nedir? (≈00:51–00:52)

  • MCP = Model Context Protocol. M: model, C: context (bağlam), P: protocol.
  • Anthropic tarafından geliştirildi (transkriptte "2004" geçiyor, doğrusu 2024) ve standart hâline geldi.
  • Uygulamamızı bir veri kaynağına ya da araca bağlarken MCP standardını kullanarak standart bir bağlantı kurmuş oluyoruz.
  • MCP, function calling'in genişletilmiş hâlidir. Bu yüzden önce function calling'i iyi anlamak gerekiyor.

Function calling akışı (≈00:52–00:58)

Akış adım adım:

  1. Kullanıcı uygulamaya bir istek gönderir (ör. ChatGPT'ye bir yazı yazmak).
  2. Uygulama bu prompt'u arka planda düzenler (eksik veya gereksiz kısımları düzeltebilir) ve modele gönderir.
  3. Model, mevcut araçların açıklamalarına, parametre açıklamalarına ve fonksiyon adlarına bakarak gerekiyorsa bir araç seçer ve gerekli parametreleri belirler. Bu kararı bir function call olarak uygulamaya gönderir ("şu fonksiyonu, şu parametrelerle kullan").
  4. Uygulama fonksiyonu çalıştırır. Önemli: aracı model çalıştırmaz; uygulamanın kendisi çalıştırır.
  5. Uygulama sonucu tekrar modele gönderir.
  6. Model bu bilgiye göre cevap üretir ve uygulamaya gönderir; uygulama da kullanıcıya döndürür.

Örnek: "3 kere 5 kaçtır?" → model "bu çarpma ile ilgili, hesap makinesi aracını kullanabilirim" der → parametreleri gönderir → uygulama aracı çalıştırır → 15 sonucu modele gider → model "cevap 15" der.

Hoca, araç yazarken açıklamaya (description), parametre açıklamalarına ve fonksiyon adına çok dikkat edilmesi gerektiğini vurguladı.

Soru: Çok fazla araç bağlanırsa bekleme süresi artar mı? Cevap: Evet, kesinlikle. Model tüm araçları, açıklamaları, parametreleri ve fonksiyon adlarını inceleyip seçim yapıyor. Fazla araç bağlanırsa model kapasitesi zorlanabilir veya geç cevap verebilir. Sadece gerekli araçları bağlayın. (Bir öğrenci, açıklamaları bölmeye gerek kalmadan modelin araç seçebildiği ve token kullanımını %32–35 azaltan yeni bir yaklaşımla ilgili bir yazı gördüğünü paylaştı; hoca yeni yaklaşımları takip etmenin önemini vurguladı ve örnek olarak CSV yerine daha kısa yanıt veren yeni bir veri formatı yaklaşımından söz etti [adı belirsiz].)

(≈01:06–01:21 arası 15 dakikalık ara.)

Client ve fonksiyon

from openai import OpenAI

client = OpenAI()

OpenAI sınıfı import edilip bir client oluşturuldu; bu client ile OpenAI modelleriyle konuşuluyor.

def add(a: int, b: int) -> int:
    """İki tam sayıyı toplar."""
    return a + b
  • def ile add adlı fonksiyon tanımlandı.
  • Type hint kullanıldı (a: int, b: int, -> int). Python'da normalde veri tipleri önceden belirtilmez; ama belirtince agent/model daha doğru yönlendirilmiş olur.
  • Docstring ("İki tam sayıyı toplar.") fonksiyonun açıklaması; model bu açıklamaya bakarak aracı kullanıp kullanmayacağına karar veriyor.

Aracı modele tanıtmak: tools

tools = [
    {
        "type": "function",
        "name": "add",
        "description": "İki tam sayıyı toplar ve sonucu döndürür.",
        "parameters": {
            "type": "object",
            "properties": {
                "a": {
                    "type": "integer",
                    "description": "Toplanacak ilk sayı"
                },
                "b": {
                    "type": "integer",
                    "description": "Toplanacak ikinci sayı"
                }
            },
            "required": ["a", "b"],
            "additionalProperties": False
        },
        "strict": True
    }
]
  • type: function → bir fonksiyon tanıtıyoruz; name → fonksiyonun adı; description → tanımı.
  • parameters bir object; properties içinde a ve b integer tipinde, açıklamalarıyla.
  • required → a ve b zorunlu.
  • additionalProperties: False → ekstra bir özellik/parametre olmasın.
  • strict: True → "Aklından başka parametre uydurma, sadece bu parametreleri kullan."
  • Bu yapının belirli bir kuralı var; ayrıntılar OpenAI dokümantasyonunda.
  • Bu hücreyle henüz model tanıtılmış olmuyor; tools sadece tanıtmak için kullanılacak değişken.

Kullanıcı mesajı: neden liste?

input_list = [
    {
        "role": "user",
        "content": "125 ile 375'i topla."
    }
]

Liste kullanılıyor çünkü karşılıklı konuşma olabilir: kullanıcı girdisi, modelin cevabı, aracın cevabı, tekrar kullanıcı girdisi… Hepsi bu listeye eklenerek konuşma geçmişi oluşur ve model kimin ne dediğini takip eder (kullanıcı sorusu → model araç kullanmış → aracın cevabı). Veri aktarımında genellikle JSON formatı kullanılıyor.

Soru: role sadece user mı olur? Cevap: Hayır. Modelden gelen cevap tekrar modele verilirken assistant rolü, aracın cevabı için araç çıktısı tipi kullanılır. Böylece model konuşma geçmişini daha iyi takip eder.

Modeli çağırmak (Responses API)

response = client.responses.create(
    model="gpt-6-luna",
    input=input_list,
    tools=tools,
)
  • OpenAI'ın Responses API'si (client.responses.create) kullanıldı.
  • Modele girdi (input) ve kullanabileceği araçlar (tools) verildi.
  • Vurgu: add fonksiyonu dışarıda; onu model değil, uygulama çalıştıracak.
print(response.output)

Çıktıda modelin bir function call yaptığı görülüyor: type="function_call", name="add", arguments (a ve b), bir call_id ve status="completed". Yani model "add aracı kullanılabilir" dedi.

Bağlamı genişletmek ve function call'u bulmak

input_list += response.output

Modelin çıktısı konuşma geçmişine eklenerek bağlam genişletildi.

tool_call = next(
    item
    for item in response.output
    if item.type == "function_call"
)

response.output içindeki öğeler arasında tipi function_call olan ilk öğe alınıyor (next ilk eşleşeni döndürür). Burada tek fonksiyon olduğu için tek seçenek var; birden fazla araç olduğunda next yapısı daha anlamlı hâle geliyor.

import json
arguments = json.loads(tool_call.arguments)

print("Modelin seçtiği araç:", tool_call.name)
print("Modelin oluşturduğu parametreler:", arguments)

Argümanlar JSON metni olarak geldiği için json.loads ile sözlüğe çevrildi. Çıktı: seçilen araç add, parametreler a=125, b=375. Model sadece hangi aracı ve hangi parametreleri kullanacağını belirliyor.

Fonksiyonu uygulama çalıştırır

result = add(**arguments)
print("Python fonksiyonunun sonucu:", result)

**arguments ile sözlükteki değerler fonksiyona parametre olarak aktarıldı. Sonuç: 500.

Araç sonucunu geçmişe eklemek

input_list.append(
    {
        "type": "function_call_output",
        "call_id": tool_call.call_id,
        "output": str(result)
    }
)
  • type: function_call_output (aracın cevabı).
  • call_id: hangi çağrının cevabı olduğunu eşleştirmek için.
  • output: sonuç; tam sayı str() ile metne çevrildi.

input_list yazdırıldığında sıra şöyle: kullanıcının girdisi (user) → modelin function call'u → function call output (500). Model geçmişi takip edip "kullanıcı bunu sormuş, ben şu aracı kullan demişim, aracın cevabı 500 gelmiş; artık cevap üretebilirim" diyor.

Son cevap

final_response = client.responses.create(
    model="gpt-6-luna",
    input=input_list,
    tools=tools
)

print("\nModelin son cevabı:")
print(final_response.output_text)

tools yine verildi; çünkü model sonuca bakıp gerekirse aracı tekrar kullanmak isteyebilir. Son cevap: "125 + 375 = 500".

Bir öğrencinin isteği üzerine hoca bütün akışı baştan özetledi (yukarıdaki adımlar). Öğrencilerin çoğu 500 sonucunu aldı.

Sunucu kodu

from mcp.server import MCPServer

mcp = MCPServer("Bootcamp MCP Server")

@mcp.tool()
def add(a: int, b: int) -> int:
    """İki tam sayıyı toplar."""
    return a + b

if __name__ == "__main__":
    mcp.run(transport="stdio")
  • mcp.server modülünden MCPServer sınıfı import edildi; sınıftan "Bootcamp MCP Server" adıyla bir örnek (instance) alınıp mcp değişkenine atandı.
  • @mcp.tool() dekoratörü: dekoratörler Python fonksiyonlarına ekstra özellik kazandırır. Fonksiyonun başına bu dekoratörü koymak, fonksiyonu bir MCP aracına çevirmek için yeterli.

Uygulama 3: Tools, Resources, Prompts (≈02:15–02:39)

Yeni dosya: 03-server.py.

from mcp.server import MCPServer

mcp = MCPServer("AI Engineering MCP Demo")

@mcp.tool()
def add(a: int, b: int) -> int:
    """İki tam sayıyı toplar."""
    return a + b

@mcp.tool()
def joke(topic: str | None = None) -> str:
    """İsteğe bağlı bir konuya göre kısa bir şaka döndürür."""
    return f"{topic} hakkında bir fıkra"

@mcp.resource("course://mcp")
def course_info() -> str:
    """MCP dersi hakkında kısa bilgi verir."""
    return (
        "Bu kaynak AI Engineering Bootcamp içindeki "
        "Model Context Protocol dersine aittir."
    )

@mcp.prompt()
def explain_mcp(level: str = "başlangıç") -> str:
    """MCP konusunu belirtilen seviyeye göre açıklayan prompt oluşturur."""
    return (
        f"Model Context Protocol konusunu {level} seviyesindeki "
        "bir öğrenciye sade örneklerle açıkla."
    )

if __name__ == "__main__":
    mcp.run(transport="stdio")

Tool (joke)

  • Yine @mcp.tool() dekoratörü + fonksiyon. Araç tasarlarken tekrar vurgu: açıklamayı yazın, parametreleri type hint ile belirtin; böyle yazınca uygulama daha iyi çalışıyor.
  • topic: str | None = None → string tipinde, isteğe bağlı parametre; hiçbir şey girilmezse None. Dönüş tipi str.
  • Hoca ilk yazdığında dönüş metninde topic'i kullanmayı unuttu ve hata aldı; f-string ile f"{topic} hakkında bir fıkra" yazınca düzeldi.
  • Yeni aracı görmek için sunucuyu Ctrl+C ile durdurup uv run mcp dev 03-server.py ile yeniden başlatmak ve Inspector'da yeniden bağlanmak gerekiyor. Tools sekmesinde artık add ve joke birlikte görünüyor. joke'a "AI" yazınca "AI hakkında bir fıkra" döndü. (Not: add'in alanlarına sadece sayı yazılabiliyor; tip tanımı arayüze de yansıyor.)

Resource (course_info)

  • @mcp.resource("course://mcp") dekoratörüne bir URI veriliyor.
  • Resource, modele ekstra bilgi sağlamak demek; model bu bilgiye bakarak cevap döndürüyor.
  • Inspector'da Resources sekmesinde bu kaynak görünüyor.

Prompt (explain_mcp)

  • @mcp.prompt() dekoratörü. level parametresi string, varsayılan değeri "başlangıç".
  • Prompt, hazır şablon oluşturup modele vermek demek.
  • Inspector'da Prompts sekmesinde explain_mcp görünüyor; level boş bırakılırsa varsayılan "başlangıç", "zor" yazılırsa "Model Context Protocol konusunu zor seviyesindeki bir öğrenciye sade örneklerle açıkla." üretiliyor.

Üç temel yapı (özet)

  • Tools: Araçlar tanımlanır (aksiyon/fonksiyon).
  • Resources: Modele ekstra bilgi verilir.
  • Prompts: Şablonlar oluşturulup modele verilir.

MCP mimarisi: Host, Client, Server (≈02:39–02:47)

  • Host: Yapay zekâ uygulamasının kendisi. Örnekler: Claude Desktop, VS Code, Streamlit ile yazdığınız bir uygulama. Görevi LLM'i çalıştırmak ve kullanıcıyla iletişim kurmak (kullanıcı input girer, output alır).
  • Client: Host ile server arasındaki iletişimi sağlar; MCP ile sunucu arasındaki bağlantıyı kurar. Bir host birden fazla MCP sunucusuna bağlanabilir (her client bir sunucu bağlantısını yönetir).
  • Server: Dış dünyadaki yetenekleri standart biçimde sunar. İçinde tools, prompts ve resources bulunur. Function calling'de bir fonksiyon/araç oluşturup onunla iletişim kuruyorduk; MCP'de bu aracı bir sunucuya çevirip birden fazla uygulamanın bağlanmasını sağlıyoruz. Yani aracı dış dünyaya açmış oluyoruz.

Hocanın gösterdiği "MCP akışı" görseli: Host (ör. Claude Desktop) → bir MCP client → MCP protokolü → MySQL sunucusu; başka bir client → dosya sistemi sunucusu; başka bir client → internet/API sunucusu.

Çalışma adımları:

  1. Host bir MCP client oluşturur.
  2. Client MCP sunucusuna bağlanır.
  3. Client sunucunun yeteneklerini keşfeder (hangi araçlar var, özellikleri ne).
  4. Client tools/list isteği gönderir ("hangi araçları kullanabilirim?").
  5. Server kullanılabilir araçları döndürür.
  6. LLM, kullanıcının isteğine en uygun aracı seçer.
  7. Client seçilen araç için sunucuya istek gönderir ("şu aracı kullanacağım").
  8. Server aracı çalıştırır.
  9. Sonuç client üzerinden host'a döner; host bunu LLM'e verir; LLM nihai cevabı üretir.

Soru: Client kodda bir sınıf örneği gibi mi düşünülmeli? Cevap: Evet; host üzerinde client'lar var ve sunucuyla bağlantıyı onlar sağlıyor. (Bir öğrenci, ChatGPT'nin de "her host birden fazla client barındırabilir, her client ayrı bir MCP sunucu bağlantısı yönetir" şeklinde sınıf örneğiyle açıkladığını paylaştı.)

Soru (SAP örneği): SAP gibi kurumsal sistemlerde veriler bir veritabanında tutuluyor ama doğrudan DB'ye erişemiyoruz; MCP burada devreye girebilir mi? Cevap: Evet; doğrudan erişilemeyen kurumsal veriye standart bir katman üzerinden erişim için MCP kullanılabilir. (Öğrenciler kendi kurumlarında Oracle/Hadoop gibi sistemlere MCP ile erişimi araştıracaklarını belirtti.)

Uygulama 4: Sunucuyu VS Code'a bağlamak — mcp.json (≈02:47–03:21)

mcp.json bir yapılandırma dosyası; sunucu ile host arasındaki bağlantıyı bu dosyayla sağlıyoruz. Burada VS Code host olarak kullanılıyor.

{
  "servers": {
    "ai-engineering-mcp": {
      "type": "stdio",
      "command": "uv",
      "args": [
        "run",
        "mcp",
        "run",
        "${workspaceFolder}/03-server.py"
      ],
      "cwd": "${workspaceFolder}"
    }
  }
}
  • servers altında ai-engineering-mcp adında bir sunucu tanımlanıyor.
  • type: stdio → standart girdi/çıktı ile iletişim.
  • command: uv → uv'yi çalıştır; args → uv run mcp run <dosya> komutu oluşur (${workspaceFolder} açık çalışma klasörü).
  • cwd → çalışma dizini.

Adımlar:

  1. Sunucuyu terminalde çalıştırma (hoca derste uv run mcp run 03-server.py benzeri komutla başlattı; ekranda bir şey çıkmıyor ama sunucu ayakta).
  2. Kritik nokta: mcp.json dosyası proje kökünde değil, .vscode klasörünün içinde olmalı (.vscode/mcp.json). Hoca önce dosyayı köke koydu, VS Code sunucuyu görmedi; .vscode klasörü oluşturup dosyayı içine taşıyınca sunucu listelendi. Alternatif (bir öğrencinin yolu): Ctrl+Shift+P → "MCP: Open User Configuration" ile kullanıcı düzeyindeki mcp.json'ı açıp yapılandırmayı oraya yapıştırmak.
  3. Ctrl+Shift+P → "MCP: List Servers" → sunucu listede görünüyor; seçilip başlatılabiliyor (durumu "Running").
  4. Dosya yolu hatalıysa VS Code "dosya bulunamadı" hatası veriyor (hoca dosya adını değiştirdiği için bir kez bu hatayı aldı; args içindeki adın gerçek dosya adıyla aynı olması gerekiyor).
  5. Ctrl+Shift+P → "Chat: Open Chat" ile yan tarafta sohbet paneli açılıyor. Örnek istek: "ai-engineering MCP sunucusundaki add aracını kullanarak 18 ile 20'yi topla." VS Code, "ai-engineering-mcp içindeki add aracını kullanmaya izin veriyor musun?" diye soruyor; izin verilince araç kullanılıyor ve sonuç (38) dönüyor.
  6. Chat için GitHub Copilot'un etkin olması (GitHub/Google hesabıyla giriş) gerekebiliyor.
  • Bir öğrenci, araç adını açıkça yazmadığında da modelin sunucuyu kendisi bulduğunu söyledi. Hoca: bazen model aracı kullanmadan kendisi cevap verebilir; aracın kullanılmasını garantilemek için istekte açıkça belirtmek iyi olur.
  • Bazı öğrencilerde "MCP: List Servers" komutu komut paletinde hiç çıkmadı; sorun derste çözülemedi. Hoca normalde VS Code'da bu seçeneğin olması gerektiğini, muhtemelen bir ayarın kapalı olduğunu söyledi (bir öğrenci Copilot önerilerini kapattığı için çıkmadığını tahmin etti).
