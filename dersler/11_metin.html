Neden gelişmiş sorgu (query) teknikleri? (≈00:15–00:20)

Klasik RAG'in hatırlatması: 1. Dokümanlarımızı bir vektör veritabanına yüklüyoruz. 2. Kullanıcı soru sorduğunda retriever soruyu alıyor, embedding'e çeviriyor. 3. Vektör veritabanında bu embedding'e en yakın parçaları (chunk) buluyor. 4. Bulunan dokümanlar + soru bağlam (context) olarak LLM'e veriliyor. 5. LLM bu bağlama bakarak cevap üretiyor.

Temiz bağlam → temiz çıktı (garbage in, garbage out). Geçen derste hep temiz, düzgün sorgular verdik. Ancak production ortamında sorgular her zaman temiz olmaz: - Soru eksik olabilir, - Soru çok genel olabilir, - Sorguda yazım hatası olabilir, - Kullanıcı birden fazla konuyu tek soruda sorabilir.

Bu durumlarda retriever yanlış chunk'ları, yani yanlış bağlamı getirir; yanlış bağlamla da LLM yanlış cevap üretir.

Bu derste görülecek 4 RAG sorgu tekniği: 1. Rewrite-Retrieve-Read: Sorguyu LLM'e yeniden yazdırıp öyle arama yapmak. 2. Multi-Query Retrieval: Soruyu çoğaltmak (aynı sorunun farklı versiyonları), hepsiyle arama yapıp sonuçları birleştirmek. 3. RAG Fusion: Multi-Query gibi birden fazla sorgu; ama gelen chunk'ları sıralamak — en çok tekrar eden chunk en üste konur, model en üsttekine daha çok dikkat eder. 4. HyDE (Hypothetical Document Embeddings): Soruya önce varsayımsal bir cevap ürettirip o cevapla arama yapmak.

1. Ortam değişkenleri ve doküman yükleme

from dotenv import load_dotenv

    )
]

Path ile dosya yolu alınıyor, read_text ile okunuyor ve LangChain'in Document sınıfına çevriliyor. Document sınıfının avantajı metadata takibi: hangi chunk'ın hangi kaynaktan geldiğini sonradan görebiliyoruz.

2. Parçalama (chunking)

from langchain_text_splitters import RecursiveCharacterTextSplitter
text_splitter = RecursiveCharacterTextSplitter(
    chunk_size=600,
    chunk_overlap=80
)

documents = text_splitter.split_documents(raw_documents)

Neden chunk'lara ayırıyoruz? - LLM'e fazla token vermek maliyeti artırır. - Gereksiz token/chunk vermek LLM'in kafasını karıştırır. - Sadece ilgili kısımları bağlam olarak verirsek bağlam iyi olur, LLM de iyi cevap üretir.

RecursiveCharacterTextSplitter hocanın "çok sevdiğimiz" dediği sınıf. Küçük metinler için chunk_size = 600 alınabileceğini daha önce söylemişti. Overlap = 80: iki chunk'ın üst üste geldiği kısım; chunk'lar arasındaki bağlantıyı (anlam sürekliliğini) korur.

3. Embedding modeli

from langchain_openai import OpenAIEmbeddings

5. Retriever

retriever = db.as_retriever(search_kwargs={"k": 2})

Retriever üç iş yapar: (1) sorguyu alıp embedding'e çevirir, (2) vektör veritabanında bu embedding'e en yakın değerleri bulur, (3) en yakın chunk'ları döndürür. Burada k=2 → en yakın 2 chunk.

9. RAG pipeline'ı: @chain dekoratörü

from langchain_core.runnables import chain

@chain
def qa(input):
    # ilgili dokümanları getir
    docs = retriever.invoke(input)

    # prompt'u formatla
    formatted = prompt.invoke({
        "context": docs,
        "question": input
    })

    # yanıt üret
    answer = llm.invoke(formatted)

    return answer

Adımlar: retriever ile en yakın dokümanları bul → context ve question ile prompt'u formatla → formatlı prompt'u LLM'e ver → cevabı döndür.

Dekoratör nedir? Bir fonksiyona ekstra özellik kazandırır. @chain ile fonksiyonumuza bir LangChain zinciri (Runnable) özelliği kazandırıyoruz; böylece .invoke() ile çağrılabilir ve pipe'lara bağlanabilir hale geliyor. İleride @tool dekoratörüyle de fonksiyonları araca (tool) çevireceğiz.

result = qa.invoke(query)
print(result.content)

Sonuç: Model; Sokrates öncesi düşünürler, Thales, Anaksimandros, Demokritos (maddenin bölünemez küçük parçalardan oluştuğunu savunan atomcu görüş) gibi isimleri saydı. Ama cevabın sonunda "ocaktaki yemeği kontrol etmeyi unutmayın" diye bir hatırlatma da yaptı! Sorguya gereksiz detay verdiğimiz için model buna da tepki verdi. Bunu istemiyoruz → Rewrite-Retrieve-Read.

Teknik 1: Rewrite-Retrieve-Read (≈00:45–00:57)

Akış: Sorguyu al → LLM'e yeniden yazdır → yeni sorguyla ilgili dokümanları getir → modele ver → cevabı al.

Sorguyu yeniden yazan prompt

rewrite_prompt = ChatPromptTemplate.from_template("""
    Provide a better search query for vector search to answer the given question.
    Remove irrelevant details.
    Return only the improved search query.

    Question: {x}

    Improved search query:"""
)

Modele şunu söylüyoruz: "Verilen soruyu cevaplamak için vektör araması için daha iyi bir arama sorgusu üret, alakasız detayları kaldır, sadece iyileştirilmiş sorguyu döndür." Prompt Türkçe de yazılabilir. Prompt'la modeli bu şekilde yönlendirmek "çok kolay, hiç zor değil."

Çıktıyı temizleyen fonksiyon

def parse_rewriter_output(message):
    return message.content.strip('"').strip("**").strip()

Model cevabında bazen tırnak işaretleri, ** (yıldızlar) gibi işaretler geliyor (geçen derste bir öğrencinin sorduğu konu). Bunları boşu boşuna modele göndermek, fazladan token harcamak istemiyoruz; o yüzden temizliyoruz.

Rewriter zinciri (LCEL pipe)

rewriter = rewrite_prompt | llm | parse_rewriter_output

LangChain'de pipe (|) bir adımın çıktısını bir sonrakine girdi olarak verir: önce prompt yeniden yazılır, LLM'e gider, sonra çıktı temizlenir.

new_query = rewriter.invoke(query)
print(new_query)

Sonuç: kalabalık sorgu temizlendi; "Antik Yunan felsefesinin önde gelen filozofları, düşünürleri, okulları…" gibi daha iyi bir arama sorgusuna dönüştü.

Birleşik zincir

@chain
def qa_rrr(input):
    # sorguyu yeniden yaz
    new_query = rewriter.invoke(input)

    print("Rewritten query:", new_query)

    # yeniden yazılmış sorguyla ilgili dokümanları getir
    docs = retriever.invoke(new_query)

    # prompt'u orijinal soru ve getirilen context ile formatla
    formatted = prompt.invoke({
        "context": docs,
        "question": input
    })

    # yanıt üret
    answer = llm.invoke(formatted)

    return answer

result = qa_rrr.invoke(query)
print(result.content)

Yeniden yazılan sorgu ekrana basıldı ("Antik Yunan felsefesinin önde gelen filozofları kimlerdir?" gibi), ardından model Sokrates öncesi isimleri (Thales, Anaksimandros, … Demokritos) içeren temiz bir cevap üretti. Sorguyu iyileştirip en yakın chunk'ları bulduğumuzda model daha iyi cevap üretti.

Teknik 2: Multi-Query Retrieval — kavram (≈01:17–01:22)

Normalde kullanıcı tek bir soru sorar; soru embedding'e çevrilir, retriever en yakın parçaları bulur. Ama tek soru her zaman gerekli bilgiyi içermeyebilir; bu tek soruyla iyi bir bağlam oluşturamayabiliriz.

Örnek: "Antik Yunan felsefesindeki önemli kişiler kimlerdir?" sorusuna en yakın chunk'lar Sokrates, Platon, Aristoteles ile ilgili olabilir. Soruyu genişletirsek daha iyi bağlam elde ederiz: - "Antik Yunan felsefesinin kurucuları kimlerdir?" - "Antik Yunan düşüncesine katkı sağlayan filozoflar kimlerdir?" - "Sokrates öncesi filozoflar kimlerdir?"

Aynı sorunun farklı versiyonlarını üretmeye Multi-Query Retrieval denir.

Akış:

Soru → (LLM) Soru 1, Soru 2, Soru 3 … → her biri embedding → vektör DB'den yakın dokümanlar
     → tüm dokümanları birleştir (tekrarları at) → context olarak LLM'e ver → cevap

"Bağlam ne kadar iyi olursa cevap o kadar iyi olur; bizim için bağlam çok çok önemli."

Tekrar eden dokümanları temizleme

Sorular aynı chunk'ları da getirebilir; aynı chunk'ı modele iki kez vermek istemeyiz. Örnek:

document_lists = [
    [doc1, doc2],
    [doc2, doc3],
    [doc1, doc4]
]

[doc1, doc2, doc2, doc3, doc1, doc4] -> [doc1, doc2, doc3, doc4]

Önce iç içe listeler tek listeye düzleştirilir (flatten), sonra tekrar edenler kaldırılır.

def get_unique_union(document_lists):
    # Liste içindeki listeleri düzleştirir ve tekrar eden dokümanları kaldırır
    deduped_docs = {
        doc.page_content: doc
        for sublist in document_lists
        for doc in sublist
    }

    # Benzersiz dokümanları liste olarak döndürür
    return list(deduped_docs.values())

Teknik 3: RAG Fusion (≈01:43–01:46 ve ≈01:52–01:53)

(Anlatımın başı kayıtta yok; aşağıdakiler kayıttaki kısım + notebook'tan.)

RAG Fusion'da da Multi-Query gibi birden fazla sorgu üretilir ve her biri için dokümanlar getirilir. Fark: gelen dokümanlar yeniden sıralanır. En çok tekrar eden doküman en üste alınır, çünkü "çok tekrar ediyorsa soruyla daha alakalıdır." Model de ilk gelene "demek ki daha önemli" diye öncelik vererek cevap üretir.

Soru → çoklu sorgu → her sorgu için vektör DB'den dokümanlar → dokümanları puanla & sırala
     (en çok/en üstte tekrar eden en üste) → context olarak LLM'e → cevap

Bu teknik derste canlı kodlanmadı; hoca notebook'u ödev olarak çalıştırmamızı istedi ("Bu akşam kendiniz çalıştırın, hata alırsanız beraber değerlendiririz"). Notebook'taki kod:

prompt_rag_fusion = ChatPromptTemplate.from_template("""
    You are a helpful assistant that generates multiple search queries based on a single input query.

    Generate multiple search queries related to: {question}

    Output 4 queries, each on a new line:
""")

def parse_queries_output(message):
    return message.content.split("\n")

llm = ChatOpenAI(model="gpt-6-luna",)

query_gen = prompt_rag_fusion | llm | parse_queries_output

def reciprocal_rank_fusion(results, k=60):

    scores = {}
    documents = {}

    for doc_list in results:
        for rank, doc in enumerate(doc_list):
            content = doc.page_content

            # Dokümanı ilk gördüğümüzde sakla
            if content not in documents:
                documents[content] = doc

            # Sırasına göre puan hesapla ve toplamına ekle
            point = 1 / (k + rank + 1)
            scores[content] = scores.get(content, 0) + point

    # Doküman metinlerini toplam puana göre sırala
    sorted_contents = sorted(
        scores,
        key=scores.get,
        reverse=True
    )

    # Sıralanmış doküman listesini oluştur
    ranked_docs = []

    for content in sorted_contents:
        ranked_docs.append(documents[content])

    return ranked_docs

Notebook notu: Multi-Query'de farklı sorgularla arama yapıp tekrarları kaldırıyorduk. RAG Fusion'da ise sonuçları ayrıca puanlayıp sıralıyoruz.

retrieval_chain = query_gen | retriever.batch | reciprocal_rank_fusion

prompt = ChatPromptTemplate.from_template("""
    Answer the following question based on this context:

    {context}

    Question: {question}
""")

@chain
def rag_fusion_qa(input):
    # RAG-Fusion ile ilgili dokümanları getir
    docs = retrieval_chain.invoke(input)

    # Prompt'u context ve soru ile formatla
    formatted = prompt.invoke({
        "context": docs,
        "question": input
    })

    # LLM ile cevap üret
    answer = llm.invoke(formatted)

    return answer

result = rag_fusion_qa.invoke(
    "Antik Yunan felsefe tarihindeki önemli isimlerden bazıları kimlerdir?"
)

print(result.content)

Hocanın notebook üzerinden özeti: birden fazla sorgu üret → satırlara ayır → modeli al, zinciri kur → getirilen dokümanları en çok tekrar edeni en üste alan fonksiyondan geçir → sorgu üretme + doküman getirme + yeniden sıralamayı tek zincir yap → prompt'u yaz → cevabı üreten fonksiyonu yaz → çalıştır.

Teknik 4: HyDE — Hypothetical Document Embeddings (≈01:46–01:54)

Klasik RAG: Soru → embedding → en yakın chunk'lar → context → cevap.

Sorun: Kullanıcının sorusu her zaman asıl cevaba yeterince yakın olmayabilir; soru embedding'i asıl chunk'ı bulamayabilir.

HyDE'de: Kullanıcının sorusu önce LLM'e verilir ve kısa, varsayımsal bir cevap ürettirilir. Sonra bu cevap embedding'e çevrilir; vektör veritabanında bu cevaba benzer chunk'lar aranır; bulunan chunk'lar context olarak modele verilir ve nihai cevap üretilir.

Örnek: "Antik Yunan felsefesindeki önemli kişiler kimlerdir?" → LLM'in varsayımsal cevabı: "Antik Yunan felsefesinde Sokrates, Platon ve Aristoteles en önemli figürler arasında yer alır…" Bu cümle soruya göre çok daha zengin bir sorgudur: daha fazla anahtar kelime içerir, dolayısıyla daha zengin bir bağlam elde edilir.

Soru → (LLM) varsayımsal kısa cevap → embedding → vektör DB'de benzer chunk'lar → context + soru → LLM → cevap

Ne zaman kullanılır? - Soru çok kısaysa (kullanıcı tek kelime/çok kısa bir şey yazdıysa), - Soru belirsizse, - Soru ile doküman arasında ifade farkı varsa (soru dokümandan farklı bir dille sorulmuşsa).

Soru: ChatGPT, Claude gibi araçlar da bu tekniği kullanıyor mu? Cevap: Büyük olasılıkla evet. Bu araçlar kullanıcının prompt'unu doğrudan modele göndermiyor; eski konuşmalara bakıp soruyu tekrar yazıyor, zenginleştiriyor, sonra modele gönderiyor. Bu, onlar için de token ve hesaplama tasarrufu sağlıyor.

Notebook'taki kod:

prompt_hyde = ChatPromptTemplate.from_template("""
    Please write a passage to answer the question.

    Question: {question}

    Passage:
""")

from langchain_core.output_parsers import StrOutputParser

llm = ChatOpenAI(temperature=0)

generate_doc = (
    prompt_hyde
    | llm
    | StrOutputParser()
)

retrieval_chain = generate_doc | retriever

prompt = ChatPromptTemplate.from_template("""
Answer the following question based on this context:

{context}

Question: {question}
""")

@chain
def qa(input):
    # HyDE retrieval chain ile ilgili dokümanları getir
    docs = retrieval_chain.invoke(input)

    # Context ve soruyu prompt'a yerleştir
    formatted = prompt.invoke({
        "context": docs,
        "question": input
    })

    # LLM ile nihai cevabı üret
    answer = llm.invoke(formatted)

    return answer

result = qa.invoke(
    "Who are some key figures in the ancient greek history of philosophy?"
)

print(result.content)

Hocanın özeti: önce prompt template, sonra prompt'u LLM ile birleştir, çıktıyı StrOutputParser ile düz metne çevir → varsayımsal dokümanı retriever'a ver → chat prompt template → cevabı üreten zincir fonksiyonu → çalıştır.
